# SysCall Harness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Docker-харнесс на openJiuwen, который за ≤1 ч и ~100K выходных токенов набирает максимум баллов на 100 задачах (`math`, `data_analysis`, `search`, `coding`), решая кодом всё, что решается кодом.

**Architecture:** Фаза 1 — детерминированные решатели по типам задач на 8 процессах (0 токенов). Фаза 2 — нераспознанные задачи уходят модели через `openjiuwen` `Model.invoke` (до 5 параллельно, по убыванию reward / оценка токенов): для math/data/search нераспознанные задачи группируются по шаблону, и на каждую группу модель один раз возвращает JSON-спецификацию для детерминированного исполнителя; что не исполнилось — модель пишет Python-программу, харнесс её исполняет; для coding модель возвращает исправленные функции, тесты гоняются локально. Учёт бюджета по `usage` каждого ответа.

**Tech Stack:** Python 3.11, `openjiuwen==0.1.19` (async `Model.invoke`), stdlib (`ast`, `csv`, `subprocess`, `concurrent.futures`, `asyncio`), pytest, Docker (`python:3.11-slim` с зафиксированным тегом), `uv` для локального окружения.

**Spec:** `docs/superpowers/specs/2026-11-07-harness-design.md`. Справочно: `../context/Task/Регламент соревнования.md`, `../context/faq.txt`, разведка API `../.recon/REPORT.md` и `../.recon/oj_smoke.py`.

## Global Constraints

- Репозиторий: `C:\D\openJiuwen\harness` (git). Все пути ниже — от его корня.
- Python `>=3.11,<3.14`; в Docker — `python:3.11.11-slim-bookworm`; все зависимости зафиксированы в `requirements.txt` (`uv pip compile`).
- `openjiuwen==0.1.19`; вызовы модели только через него.
- Запуск: `python /app/run_agent.py --tasks-dir /data/tasks`; env `LLM_BASE_URL`, `LLM_API_KEY`, `BUDGET` (по умолчанию `100000`). `OUT` не используется.
- Стоимость вызова в бюджете: `prompt_tokens / 10 + completion_tokens` (рассуждения входят в `completion_tokens`).
- Модели: `qwen3.6-35b-a3b-noreason` (по умолчанию), `qwen3.8-27b` с `reasoning_effort="low"` (повтор для coding). Другие две модели не используются.
- Не больше 5 одновременных запросов к модели; не больше 8 процессов фазы 1.
- `answer.txt` — в каталоге задачи рядом с `task.json`, одна строка ответа + `\n`; запись атомарная (tmp + `os.replace`) с `fsync`. Для невыполнимой задачи файл не создаётся.
- Тестовые файлы задач (`test_*.py`) никогда не изменяются.
- Контейнер `--read-only`: писать можно только в каталог задач и `/tmp`; лог траектории — `/tmp/harness/trajectory.jsonl` (env `HARNESS_LOG_DIR` переопределяет).
- Процесс всегда завершается с кодом 0; ни одно исключение одной задачи не останавливает прогон.
- Внешняя сеть — только `LLM_BASE_URL`. Ключей в репозитории нет; `../context/keytoconnect.txt` не копируется в репозиторий.
- Коммиты без строк `Co-Authored-By` и аналогичных трейлеров (глобальное правило пользователя).
- Подпроцессы Python запускаются через `sys.executable -B` (без `.pyc`), не `python3` (локальная разработка идёт на Windows). На Linux каждому подпроцессу задаются `RLIMIT_AS = 2 ГБ` и `start_new_session=True`; по таймауту убивается вся группа (`os.killpg`). На Windows лимиты пропускаются.
- Решатели и программы модели работают только во временных копиях `workspace` в `/tmp` (`tempfile.mkdtemp(dir=$TMPDIR)`); в настоящий `workspace` пишется только итоговый `mylib.py` (coding), после чего удаляется `workspace/__pycache__`.
- Ответ пишется всегда, когда решатель получил хоть какой-то детерминированный ответ (штрафа за неверный нет): пустая выборка или неизвестный продукт → `0`, однофамильцы → первый по имени файла. `infeasible` — только когда ответа нет вовсе (человек или компания не найдены, деление на 0); такие задачи не уходят модели.
- Все пороги и таймауты — в `harness/config.py` (одно место): `PHASE1_WORKERS=8`, `CODING_TIME_LIMIT=90`, `PHASE1_TIMEOUT={"coding": 100, "default": 15}`, `LLM_CONCURRENCY=5`, `LLM_TIMEOUT=180`, `DEADLINE_S=3300`, `STOP_NEW_BEFORE_DEADLINE_S=150`, `RESERVE_FRACTION=0.01`, `TIMEOUT_CHARGE=1500` (сколько списывать за вызов, оборвавшийся по таймауту).
- Перед импортом `openjiuwen` процесс делает `os.chdir` в `$HARNESS_LOG_DIR` (по умолчанию `/tmp/harness`): библиотека пишет логи в `./logs/` относительно текущего каталога, а `/app` в контейнере только для чтения.

## Review Focus

1. Формулировка задачи слегка отличается от шаблона (другой регистр, лишние пробелы, неизвестное предложение) — решатель возвращает `unparsed`, а не падает и не пишет неверный ответ по частичному разбору. Тесты в задачах 2–4.
2. Мутант в coding зацикливается или съедает память — кандидат отбрасывается по таймауту, задача продолжается. Тест в задаче 5.
3. Бюджет кончается посреди 5 параллельных вызовов — новые вызовы не стартуют, уже решённые ответы на диске, процесс завершается с кодом 0. Тест в задаче 10.
4. Каталог задачи без `task.json`, с битым JSON или без `workspace/` — задача пропускается, прогон идёт дальше. Тест в задаче 1.
5. Программа от модели печатает лишнее, падает или пишет пустой вывод — ответ нормализуется по `check` (`exact_int`: последнее целое в выводе, `389.0` → `389`; `exact_str`: последняя непустая строка без кавычек и префикса `Answer:`); падение — одна повторная попытка со stderr; пустой вывод после повтора → ответ не пишется. Тест в задаче 8.
6. Каталог задач на хосте принадлежит другому пользователю (mode 755), а в контейнере нет `CAP_DAC_OVERRIDE` — `os.replace` во временный файл невозможен; запись откатывается на `open('w')` + `fsync` прямо в `answer.txt`. Тест в задаче 1 (подмена `os.replace`, бросающая `PermissionError`) и проверка в задаче 11.

  - `harness.solvers.math_solver.solve(task: Task) -> SolveResult` — `parse` + `execute`
  - `harness.solvers.math_solver.parse(instruction: str) -> dict | SolveResult` — спецификация или `unparsed`/`infeasible`
  - `harness.solvers.math_solver.execute(spec: dict) -> SolveResult` — спецификация `{"start": int, "ops": [[op, n], ...]}`, `op` ∈ `"+", "-", "*", "//"`, `n` — int; не та форма или типы → `unparsed`; `["//", 0]` → `infeasible`

Разбор по предложениям в спецификацию; каждое предложение должно совпасть ровно с одним правилом, иначе `unparsed`. Правила (регистр игнорируется, необязательное `Then ` в начале):

| Предложение | Операция |
|---|---|
| `A warehouse starts with N boxes.` | `x = N` |
| `the stock is split equally into K warehouses and it keeps one share (rounded down).` | `K == 0` → `infeasible`; иначе `x //= K` |
| `the stock is doubled by merging with a sister warehouse.` | `x *= 2` |
| `It ships A boxes per day for D days.` | `x -= A*D` |
| `It receives R deliveries of B boxes each.` | `x += R*B` |
| `How many boxes does it have at the end?` | вопрос; обязателен |

Нет начального значения или вопроса — `unparsed`.

**Interfaces:**

- Produces:
  - `harness.solvers.data_solver.solve(task: Task) -> SolveResult` — `parse` + `execute`
  - `harness.solvers.data_solver.parse(instruction: str) -> dict | SolveResult`
  - `harness.solvers.data_solver.execute(spec: dict, workspace: Path, check: str | None) -> SolveResult` — спецификация `{"file": str, "metric": "sum_units" | "sum_revenue" | "count_orders" | "avg_price" | "avg_units", "product": str | None, "region": str | None, "month_from": int | None, "month_to": int | None}`; лишние/неверные ключи → `unparsed`

Разбор вопроса в спецификацию:
- файл: `The file (\S+\.csv) has columns ([\w,]+)` — колонки берутся из файла, не из текста;
- метрики: `How many units` → `sum(units)`; `total revenue` / `revenue` → `sum(units*price)`; `How many orders` → `count`; `average price` / `average units` → среднее; при `exact_int` округление половины вверх (`Decimal.quantize(ROUND_HALF_UP)`), правило фиксируется в README;
- фильтры: `of product '(\w+)'`, `in region '(\w+)'`, `in months? A through B inclusive`, `in month A`;
- всё, что после удаления распознанных фрагментов осталось содержательным, → `unparsed`.

`infeasible`: файла нет или нужной колонки нет. Значение фильтра, которого нет в данных, месяц вне 1–12, пустая выборка — `solved` с ответом `0` (по Global Constraints ответ пишется всегда, когда он есть).

### Task 4: Решатель search

**Files:**
- Create: `harness/solvers/search_solver.py`
- Test: `tests/test_search_solver.py`

**Interfaces:**
- Consumes: `Task`, `SolveResult`, `strip_boilerplate`
- Produces:
  - `harness.solvers.search_solver.load_kb(kb_dir: Path) -> dict[str, dict[str, str]]` — имя из строки `# Name` → поля `Ключ: значение`
  - `harness.solvers.search_solver.solve(task: Task) -> SolveResult` — `parse` + `execute`
  - `harness.solvers.search_solver.parse(instruction: str) -> dict | SolveResult`
  - `harness.solvers.search_solver.execute(spec: dict, workspace: Path) -> SolveResult` — спецификация `{"entity": str, "path": [str, ...], "field": str}`: от `entity` пройти по полям `path` (каждое — имя другой сущности, например `"Employer"`, `"Mentor"`), вернуть поле `field` последней; имена полей — как в файлах kb (любой ключ, не только перечисленные ниже)

Грамматика сущности `E := Name | E's employer | E's mentor | the employer of E | the mentor of E`. Вопросы:

| Вопрос | Поле |
|---|---|
| `In which year was E born?` | `Born` |
| `In which year was E founded?` | `Founded` |
| `In which city is the headquarters of E?` / `Where is E headquartered?` | `Headquarters` |
| `Who is the mentor of E?` / `Who is E's mentor?` | `Mentor` |
| `Which company does E work for?` / `Who employs E?` / `Who is E's employer?` | `Employer` |

Имена сравниваются точно (после `strip` и схлопывания пробелов, без учёта регистра). Сущность или поле не найдены → `infeasible`. Имя встречается в двух файлах → ответ по первому файлу в порядке имени файла. Вопрос не разобран → `unparsed`.
