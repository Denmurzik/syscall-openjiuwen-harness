# SysCall harness (openJiuwen Challenge 2026)

Харнесс решает задачи четырёх типов (math, data_analysis, search, coding) и для каждой выполнимой пишет `answer.txt`. Большую часть задач он решает детерминированно, без обращений к LLM; модель вызывается только для того, что не удалось разобрать правилами. Вызовы модели идут через `openjiuwen==0.1.19` (`Model.invoke`, провайдер OpenAI-совместимый, `harness/llm.py`); решатели, планировщик и учёт токенов написаны командой.

## Словарь

- **Фаза 1** — решатели без модели (0 токенов). **Фаза 2** — всё, что фаза 1 не решила, с вызовами модели: **2a** (JSON-спецификация на группу однотипных задач), **2c** (арбитраж coding), **2b** (программа или патч от модели на отдельную задачу). Порядок: 2a, 2c, 2b, повторный проход, финальный REASON-проход.
- **Юнит** — одна единица работы фазы 2 (группа 2a, батч 2a, арбитраж 2c или задача 2b); планировщик упорядочивает и запускает юниты.
- **Статусы задачи**: `solved` (ответ записан), `infeasible` (ответа не существует, `answer.txt` не создаётся), `unparsed` (решить не удалось; ответа нет, либо только запасной).
- **Запасной ответ (best guess)** — лучшее предположение, которое решатель отдаёт вместе с `unparsed`, когда надёжно решить нельзя. Он пишется на диск сразу и заменяется, если позже найдётся настоящий ответ.
- **Модели** (`harness/config.py`): `MODEL_FAST` = qwen3.8-27b-noreason, `MODEL_ALT` = qwen3.6-35b-a3b-noreason, `MODEL_REASON` = qwen3.8-27b (с `reasoning_effort=low`).
- **Расход** — completion-токены + prompt/10 (рассуждения входят в completion).

## Формат задач

Каталог задач содержит каталоги вида `<task_id>/` (примеры организаторов лежат в `tests/fixtures/examples/`):
- `task.json`: `task_id`, `task_type`, `instruction`, `reward` (баллы за задачу), `check` (`exact_int`, `exact_str` или `unittest`). В примерах есть ещё `expected`; в финальном наборе его не будет, харнесс его не читает.
- `workspace/` (если есть): для data_analysis `sales.csv`; для search папка `kb/` с markdown-файлами о людях и компаниях (поля Born, Employer, Mentor, Founded, Headquarters); для coding `mylib.py` и `test_mylib.py`. У math рабочего каталога нет.
- Ответ — файл `answer.txt` рядом с `task.json`; для coding это слово `DONE`, а исправление записывается в `workspace/mylib.py`.

Харнесс пропускает каталоги `__MACOSX` и начинающиеся с точки, допускает вложенность `каталог/каталог/<задачи>`, читает `task.json` с BOM; без числового `reward` берёт 1.0.

## Сборка и запуск

Команда жюри (из регламента; в регламенте у `docker build` нет контекста, здесь добавлена точка):

```bash
mkdir -p "$OUT" && chmod 777 "$OUT"

docker build -t "hack:latest" . && \
timeout -k 1000s 1h docker run --rm --name "run-${TEAM}" \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  "hack:latest" \
  /app/run_agent.py --tasks-dir /data/tasks
```

`TEAM` — имя команды, `TASKS` — каталог с задачами на хосте, `OUT` — каталог на хосте (по ответам организаторов 2026-11-09, `OUT` устарел: считается `answer.txt`), `hack-net` — сеть, которую создаёт жюри. `docker build` выполняется из корня репозитория. В контейнер попадают только `LLM_BASE_URL`, `LLM_API_KEY` и `TASKS` как каталог `/data/tasks`; `BUDGET` и `OUT` не передаются, поэтому в прогоне жюри действует бюджет по умолчанию 100000 (ориентир из ответов организаторов: 100K), а результат — только `answer.txt` в каталоге каждой задачи. Код выхода всегда 0.

**Локальный запуск без Docker и без ключа** (Python 3.11+; работает только фаза 1):

```bash
pip install -r requirements.txt -r requirements-dev.txt
python -m tools.gen_tasks --out /tmp/set --n 100 --seed 1    # /tmp/set/tasks и /tmp/set/hidden
HARNESS_LOG_DIR=/tmp/set/log python run_agent.py --tasks-dir /tmp/set/tasks
python -m tools.evaluate --run /tmp/set --log /tmp/set/log/trajectory.jsonl
```

**Локальный запуск в Docker с настоящим прокси** (те же флаги, что у жюри, плюс сеть, бюджет и каталог траекторий в примонтированном каталоге):

```bash
docker network create hack-net
docker build -t hack:latest .
docker run --rm --network hack-net -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET=100000 \
  -e HARNESS_LOG_DIR=/data/tasks/_harness_log \
  -v "$PWD/set/tasks:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

(`python -m tools.gen_tasks --out set ...` создаёт `set/tasks`; затем `python -m tools.evaluate --run set --log set/tasks/_harness_log/trajectory.jsonl`. Предупреждение «skipping task dir _harness_log» в stderr безвредно.) `tests/chaos/fakeproxy.py` — подставной прокси для проверки без ключа (`python -m pytest -m chaos`).

Образ и сборка: `python:3.11.11-slim-bookworm`, зависимости закреплены в `requirements.txt` (`openjiuwen==0.1.19` и транзитивные версии, собрано под linux x86_64), при запуске ничего не скачивается. Локально собранный образ `hack:latest` весит 1,42 ГБ по `docker images` (лимит 4 ГБ), файлы репозитория занимают около 1 МБ (лимит 100 МБ).

Раскладка: `run_agent.py` (точка входа), `harness/` (`solvers/` — фаза 1; `json_route.py`, `arbitrate.py`, `llm_routes.py` — фаза 2; `llm.py` — клиент модели; `budget.py`, `estimator.py`, `scheduler.py`), `tools/` (генератор задач, оценщик, стенды), `tests/`, `docs/trajectories/`.

### Переменные окружения

- `LLM_BASE_URL`, `LLM_API_KEY` — прокси организаторов. Если не заданы, работает только фаза 1.
- `BUDGET` — бюджет токенов (умолчание 100000). `HARNESS_LOG_DIR` — каталог траекторий и логов (умолчание `<tempdir>/harness`, то есть `/tmp/harness`; на `tmpfs` с `--rm` он исчезает после прогона).
- `TASKS` — запасной каталог задач; `OUT` или `--out` — необязательный файл `{task_id: answer}`, который переписывается после каждого ответа. Он не нужен, считается `answer.txt`. Каталог задач берётся из `--tasks-dir`, позиционного аргумента, `TASKS`, `/data/tasks` (первый, где есть `task.json`); выбор пишется в stderr.
- Ручки времени и параллельности, все необязательны; пустое, нечисловое, отрицательное или бесконечное значение заменяется умолчанием с одним предупреждением (кроме `HARNESS_LLM_CONCURRENCY`: она заменяется молча): `HARNESS_LLM_TIMEOUT` — таймаут вызова модели, с (180); `HARNESS_DEADLINE_S` — общий дедлайн, с (3300; лимит жюри 3600); `HARNESS_STOP_NEW_BEFORE_DEADLINE_S` — за сколько секунд до дедлайна новые юниты не стартуют (150); `HARNESS_RETRY_DELAYS` — паузы повтора на 429 и при сбоях прокси, с, через запятую (`2,4,8,16,30`); `HARNESS_PROXY_DEAD_S` — сколько секунд без единого успешного ответа считать прокси мёртвым (по умолчанию равно дедлайну); `HARNESS_PHASE1_TIMEOUT_CODING` и `HARNESS_PHASE1_TIMEOUT_DEFAULT` — таймаут фазы 1 на coding-задачу и на остальные, с (100 и 15); `HARNESS_LLM_CONCURRENCY` — одновременных вызовов модели (3: потолок аккаунта у dev-провайдера, финальный прокси допускает до 5); `HARNESS_BATCH_2A` — батчинг групп в 2a (включён, `0`/`false` отключает).

### Запись ответов

Каждый ответ пишется сразу после решения: временный файл рядом, `fsync`, `os.replace`; если каталог не позволяет создавать файлы, пишется напрямую в `answer.txt`. В `/app` ничего не пишется. Каталог задач должен быть доступен на запись для root в контейнере (организаторы 2026-11-09 подтвердили, что будет); при недоступности в stderr печатается `TASKS DIR NOT WRITABLE: uid=… owner=… mode=…`. В конце на stdout выводится `solved=… infeasible=… unparsed=… spent=…`.

## Архитектура

### Фаза 1: решатели без модели

`harness/solvers/*`, 8 процессов (`spawn`), жёсткий таймаут на задачу: 15 с, для coding 100 с; coding-решатель останавливается сам за 15 с до этого (85 с), чтобы успеть записать предварительный ответ.
- **math**: разбор предложения по грамматике шаблонов и вычисление шагами-выражениями. Отрицательный запас ответом не считается (см. запасные ответы).
- **data_analysis**: разбор вопроса в запрос к CSV: суммы, количество заказов, средние, `top_product_*` и `top_region_*`, `max_units`/`min_units`, округление «rounded to N decimal places». Свободный разбор принимает только вопросы, где неизвестных слов нет; любой неизвестный квалификатор («excluding», «first 3 months», «per unit») даёт `unparsed`, а не угаданный ответ.
- **search**: разбор цепочки запросов к базе знаний (человек → работодатель → город штаб-квартиры и т. п.). Поле, не подходящее по виду сущности (Founded у человека), и обратные связи («кого наставляет X») не угадываются.
- **coding**: ремонт кода однотокенными мутациями; кандидаты проверяются на видимых тестах во временной копии каталога; найденное исправление записывается в настоящий `workspace/mylib.py`. Если подходящих исправлений несколько, решатель группирует их по поведению на видимых вызовах и выбирает по правилу ничьей (`coding_solver._edit_rank`: разворот сравнения лучше смены строгости, она лучше отрицания; константа, сдвинутая к нулю, лучше сдвинутой от нуля; исправление, убирающее пустую операцию вроде `x * 1`, лучше создающего её). Задача получает предварительный ответ `DONE` и идёт в арбитраж 2c. Перебор ограничен (400 мутантов, 9 вариантов на функцию) и касается только функций верхнего уровня.

**Предварительные ответы.** Ответ, записанный как предварительный (частичный ремонт или неоднозначный выбор), остаётся в `answer.txt`, а задача идёт в фазу 2 за улучшением. Неудачная поздняя попытка его не отзывает.

**Запасные ответы.** Решатель возвращает `unparsed` вместе с запасным ответом, если решить надёжно нельзя: math при отрицательном запасе, data при ничьей за первое место, search при расхождении двух чтений вопроса. Так же поступают 2a и 2b, если ответ и после повтора не прошёл проверку формы (такая догадка `shape_mismatch` занимает только пустое место). Запасной ответ пишется на диск сразу, а не в конце: прогон могут остановить без предупреждения. Он заменяется настоящим ответом; вердикт `infeasible` фазы 2 его удаляет.

### Фаза 2: модель

Для задач, которые фаза 1 не решила (или решила предварительно).

- **2a.** Нераспознанные math/data/search задачи группируются по шаблону (`harness/templates.py`: числа и имена заменяются слотами). Модель один раз на группу выдаёт JSON-спецификацию (`harness/json_route.py`), её исполняют те же исполнители, что в фазе 1. Для math это `{"start": N, "steps": ["x-{N2}*{N3}", "x-x//4"]}` (шаги вычисляет безопасный AST-вычислитель: только `x`, целые, `+ - * //`); для search `{"entity": "{E1}", "hops": ["Mentor", "Employer", "Headquarters"]}`. Спецификация `{"impossible": true}` разрешена для величин, которых нет в данных. Расход на группу: обычно один вызов, плюс повтор при битом JSON и один повтор на `MODEL_ALT` при ответе не той формы (`harness/shape.py`: год из 4 цифр, имя, целое) или при числе шагов меньше числа операций в тексте. Вопросы, идущие по связи в обратную сторону, в 2a не задаются, а сразу уходят в 2b. Батчинг: до 4 мелких групп одного типа (до 2 задач в каждой) получают спецификации одним вызовом; негодный элемент решается своим вызовом.
- **2c.** Арбитраж неоднозначных coding-задач (`harness/arbitrate.py`): `MODEL_FAST` и `MODEL_ALT` независимо отвечают номером варианта (`max_tokens` 8). Выбор меняется только если обе назвали один и тот же вариант, отличный от детерминированного, и только после полностью зелёного видимого прогона; иначе остаётся детерминированный выбор. Замер раунда 3 на 100 трудных coding-задачах: 92/100 до, 95/100 после (одна модель, без правила ничьей и с ним вместе с согласием двух моделей); цена около 87 токенов на задачу против 43.
- **2b.** Запасной путь. Для math/data/search: программа от `MODEL_FAST` (до двух попыток, вторая с ошибкой первой, `max_tokens` 400), исполняется отдельным процессом на копии каталога (до 20 с); при ответе не той формы один вызов на `MODEL_ALT`. Если модель недоступна, берётся следующая (`chat_or_alt`). Для coding лестница патчей: `MODEL_FAST` (400 токенов), `MODEL_ALT` (600), `MODEL_REASON` (3000, выполняется при награде ≥ 3 или если осталось больше половины бюджета); следующая ступень стартует от частичного результата предыдущей.
- **Повторный проход** для юнитов, у которых вызов не получил ответа от прокси.
- **Финальный REASON-проход.** Если бюджета потрачено меньше половины, для не более чем 10 нерешённых math/data/search задач с наградой не ниже медианы (по всем задачам, лучшие первыми) делается по одному вызову `MODEL_REASON` с просьбой написать программу (3000 токенов). Потолок в 10 вызовов не зависит от учёта: прокси может не вернуть usage.

## Оценка расхода и отбор задач

`harness/estimator.py`: оценка вызова до его выполнения = длина контекста в символах / 3 (символов на токен) / 10 (вес prompt) + базовая константа маршрута: JSON-спецификация 80, программа 120, coding 400 (ответ модели). Для coding контекст — `mylib.py` + тесты + 2000 символов запаса.

Как оценка влияет на работу:
- юниты 2a и 2b упорядочиваются по `reward / оценка` (по убыванию); арбитраж 2c дёшев и идёт отдельным этапом до 2b;
- перед запуском юнит проверяется: если его оценка не помещается в остаток бюджета за вычетом резерва, он пропускается и берётся следующий, более дешёвый;
- перед каждым вызовом цена вызова резервируется под учёт: полный `max_tokens`, если помещается, иначе ограниченный остатком; вызов с лимитом меньше 100 токенов (1000 для рассуждений) не делается.

Точность оценки невелика: на шести юнитах «программа» из прогонов ниже фактический расход составил от 0,8 до 4,3 оценки (один из шести дороже в 4,3 раза). Для выбора порядка этого достаточно, для строгого прогноза нет.

## Бюджет и защита от обрыва

Организаторы (2026-11-09): прокси при исчерпании бюджета ничего не присылает, запуск просто останавливается, засчитывается то, что успело записаться. Поэтому харнесс не ждёт сигнала, а следит сам:
- свой счётчик `TokenLedger` (`harness/budget.py`) по usage ответа прокси; если usage нет, списывается оценка (prompt = длина сообщений / 4, completion = лимит вызова);
- 5 % бюджета не тратится вообще (резерв), оставшееся резервируется на вызовы в полёте (`hold`);
- вызов, завершившийся таймаутом или оборванным соединением, списывается фиксированной суммой (`TIMEOUT_CHARGE` 1500, не больше стоимости самого вызова); ответ 402/403 считается исчерпанием бюджета;
- каждый ответ и каждый запасной ответ пишутся на диск сразу, поэтому остановка в любой момент не теряет уже найденное;
- общий дедлайн 3300 с: после него новые юниты фазы 1 не стартуют, юниты фазы 2 прекращаются; за 150 с до дедлайна новые юниты фазы 2 не начинаются.

**Сбои прокси.** Состояние здоровья ведётся по каждой модели. Ошибка 5xx или соединения повторяется с паузами (`HARNESS_RETRY_DELAYS`, затем удвоение до 60 с); ответ 429 — по тем же паузам. Если сбоит одна модель, а другие отвечают, вызов уходит на другую; если не отвечает ни одна, харнесс ждёт, а не сдаётся, и объявляет прокси мёртвым только после `HARNESS_PROXY_DEAD_S` секунд (по умолчанию весь дедлайн) без единого успешного ответа. Ответ 400 на `response_format`/`extra_body` клиент один раз повторяет без них и дальше их не посылает.

## Невыполнимые задачи

Задача невыполнима, если ответа нет при имеющихся данных (человека или компании нет в базе, деление на 0, нет колонки или файла, запрошена величина вне данных). Такой задаче `answer.txt` не создаётся: по ответам организаторов файл не создаётся, баллов за пропуск нет.

Кто и когда признаёт задачу невыполнимой:
- Фаза 1 (0 токенов): по результату исполнения спецификации. Примеры: data-запрос про скидку, налог, прибыль и подобное при отсутствии такой колонки; неизвестная начальная сущность в search; деление на ноль в math.
- coding: строгое доказательство противоречия видимых тестов (`coding_solver.provable_contradiction`): один и тот же вызов чистой функции с литеральными аргументами должен давать два разных ожидаемых значения; учитываются только прямые `assertEqual` без ветвлений, чистота функции проверяется. Решение принимается только по доказательству: при сомнении задача идёт дальше, потому что ложный `infeasible` стоит награды за задачу. В фазе 2 доказательство проверяется до вызова модели.
- 2a: окончательно принимается только `solved` и вердикты, не зависящие от разбора моделью (деление на ноль, отсутствие начальной сущности, дословно стоящей в инструкции). Остальные `infeasible` считаются `unparsed`, и задачу пробует 2b. Начальная сущность, совпадающая по словам ровно с одной страницей базы («Jonas Dubois» и «Jonas T. Dubois»), тоже считается нашей ошибкой разбора, а не отсутствием.
- 2b и финальный REASON-проход: программа модели, напечатавшая последней строкой `IMPOSSIBLE`. Токены на вызов уже потрачены.

Известное ограничение: часть невыполнимых задач получает ответ (в прогонах ниже 1 из 20 и 3 из 18), если разбор приводит их к осмысленному значению, например пустое среднее даёт `0`. Это осознанное приведение: такой ответ по регламенту просто не засчитывается.

## Траектории

Файл `trajectory.jsonl` в `HARNESS_LOG_DIR`: события всех задач в порядке выполнения, пишет `harness/scheduler.py`, каждая запись сбрасывается на диск сразу. Файл дописывается, а не перезаписывается: при повторном запуске с тем же каталогом прогоны смешиваются. В Docker по команде жюри каталог лежит в `tmpfs` и исчезает с контейнером; чтобы забрать траекторию, задайте `HARNESS_LOG_DIR` в примонтированный каталог (см. выше).

Поля записи: `phase` (1 или 2), `task_id`, `status`, `cost`, `elapsed` (с), `note`; у фазы 2 ещё `unit`, `model`, `calls`. `cost` — сумма стоимости собственных вызовов юнита (у фазы 1 — 0). `unit`: `group:<тип>:<число задач>`, `batch:<тип>:<число групп>`, `arbitrate:<task_id>`, `reason:<task_id>` или `<task_id>` для 2b. `calls` — список `{model, prompt_tokens, completion_tokens, cost}`, у неудавшихся вызовов ещё `error`. Стоимость группы записывается на её первого участника. Служебные статусы: `unit` (вызовы юнита без закрепившейся задачи), `deadline`, `budget_exhausted`, `error`, `unattributed` (расхождение с учётом бюджета, чтобы сумма `cost` по файлу равнялась расходу). Пример записи:

```json
{"phase": 2, "task_id": "data_analysis_0074", "status": "solved", "unit": "data_analysis_0074", "model": "qwen3.8-27b-noreason", "cost": 112.0, "calls": [{"model": "qwen3.8-27b-noreason", "prompt_tokens": 280, "completion_tokens": 84, "cost": 112.0}], "elapsed": 1.371, "note": "model program"}
```

Приложены траектории (`docs/trajectories/`):
- `2026-11-09-d0008e4-live4.jsonl` и `2026-11-09-d0008e4-llm3.jsonl` — два прогона ниже (коммит d0008e4);
- `2026-11-08-train.jsonl` и `2026-11-08-live-r2.jsonl` — прогоны раундов 1 и 2 на более ранних версиях кода; в первом поле `run` отличает прогоны.

## Безопасность

Изоляцию обеспечивает контейнер: корень только для чтения, без capabilities, закрытая сеть с выходом только на прокси организаторов, лимиты памяти и PID.

Единственная сетевая цель харнесса — `LLM_BASE_URL`; ключ берётся из `LLM_API_KEY`, нигде не записывается и не передаётся подпроцессам (`harness/proc.py`: `LLM_API_KEY`, `LLM_BASE_URL`, `BUDGET` убираются из окружения). Код задачи и программы модели запускаются только через `run_python`. Других адресов в коде образа нет, при запуске ничего не скачивается.

Локальных нейросетевых моделей нет. `transformers` и ещё несколько пакетов приходят транзитивно из `openjiuwen`; харнесс их не импортирует.

Код задачи и программы модели выполняются отдельным процессом на временной копии каталога задачи, с лимитами на posix: память `RLIMIT_AS` 2 ГиБ, время CPU `RLIMIT_CPU` (таймаут × 4 + 5 с), размер файла `RLIMIT_FSIZE` 1 ГиБ, вывод обрезается до 8 КБ, один поток BLAS/OpenMP. Это защита от ошибок программ, а не граница безопасности: сетевой и файловой изоляции у процесса нет, она остаётся за контейнером.

`kill`, `killpg` и чтение `/proc` используются только для завершения собственных зависших потомков по таймауту. Контейнер работает от root (без capabilities), потому что владелец смонтированного `/data/tasks` заранее неизвестен.

## Результаты

Два прогона Docker по команде жюри (`BUDGET=100000`, реальная модель через прокси, коммит d0008e4); траектории в `docs/trajectories/`, подсчёт `python -m tools.evaluate --run <набор> --log <траектория>` (score — сумма наград верно решённых задач с учётом скрытых тестов coding; max — сумма наград выполнимых задач).

| Прогон | Набор | score / max | токены | время |
|---|---|---|---|---|
| live4 | 100 задач `tools.gen_tasks`, сложность hard, половина формулировок переписана `tools.paraphrase` (seed 91), 20 невыполнимых | 256 / 256 | 3747 | 130 с |
| llm3 | 113 задач, на которых фаза 1 не решила ни одной, 18 невыполнимых | 295 / 295 | 10091 | 118 с |

- live4: итог `solved=81 infeasible=17 unparsed=2`; решено верно: coding 17/17, data 20/20, math 20/20, search 23/23. Из 20 невыполнимых без ответа остались 19.
- llm3: итог `solved=98 infeasible=14 unparsed=1`; data 35/35, math 28/28, search 32/32 (coding в наборе нет). Все решения получены в фазе 2, 35 вызовов модели. Из 18 невыполнимых без ответа остались 15.
- `deadline`, `budget_exhausted` и `error` в обеих траекториях нет.

Наборы создаёт наш генератор, поэтому цифры фазы 1 на нём измеряют подгонку под наш генератор, а не точность на задачах организаторов. Охват формулировок организаторов неизвестен: нераспознанное уходит в 2a/2b. `MODEL_FAST` выбран замером на нераспознанных math-задачах фазы 2a (`gen_tasks --novel 1.0 --seed 31`: 12 из 12 против 2 из 12 у `MODEL_ALT`); на data/search и coding выборка мала или замера нет.
