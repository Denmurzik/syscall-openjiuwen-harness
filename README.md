# SysCall harness (openJiuwen Challenge 2026)

Харнесс решает задачи четырёх типов (math, data_analysis, search, coding) с минимальным расходом токенов. Большую часть задач он решает детерминированно, без обращений к LLM; модель вызывается только для того, что не удалось разобрать правилами.

## Сборка и запуск

Команда жюри (из регламента):

```bash
mkdir -p "$OUT" && chmod 777 "$OUT"

docker build -t "hack:latest" . && \
timeout -k 1000s 1h docker run --rm --name "run-${TEAM}" \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  "hack:latest" \
  /app/run_agent.py --tasks-dir /data/tasks
```

- Образ: `python:3.11.11-slim-bookworm`, зависимости закреплены в `requirements.txt` (`openjiuwen==0.1.19` и транзитивные версии, собрано под linux x86_64). Ничего не скачивается при запуске, ключей в образе и репозитории нет.
- Переменные окружения: `LLM_BASE_URL`, `LLM_API_KEY` (выдаёт жюри), `BUDGET` — бюджет токенов (по умолчанию 100000), необязательная `HARNESS_LOG_DIR` — каталог траекторий (по умолчанию `<tempdir>/harness`, то есть `/tmp/harness`). `OUT` не используется.
- Результат: `answer.txt` в каталоге каждой задачи (`/data/tasks/<task>/answer.txt`). Код выхода всегда 0.
- Запись `answer.txt`: временный файл рядом + `fsync` + `os.replace`; если каталог не позволяет создавать файлы, запись идёт напрямую в `answer.txt`. Каждый ответ пишется сразу после решения, а не в конце. В `/app` ничего не пишется (файловая система только для чтения, рабочие данные уходят в `/tmp`).
- Каталог задач должен быть доступен на запись для root внутри контейнера: при `--cap-drop ALL` каталог другого владельца с правами 755 блокирует запись каждого `answer.txt` (обходного пути внутри контейнера нет).
- Если `LLM_BASE_URL`/`LLM_API_KEY` не заданы, работает только фаза 1.

## Архитектура

### Фаза 1: детерминированные решатели (0 токенов)

`harness/solvers/*`, 8 процессов (`spawn`, таймаут на задачу: 15 с, для coding 100 с; лимиты CPU/памяти на процесс (`proc.make_limits`) действуют на подпроцессы тестов и программ, а не на сами рабочие процессы):

- math: разбор предложения по грамматике шаблонов и вычисление;
- data_analysis: разбор запроса в спецификацию запроса к CSV и выполнение;
- search: разбор цепочки запросов к базе знаний (kb chain spec);
- coding: ремонт кода инверсными однотокенными мутациями; кандидаты проверяются на видимых тестах только во временных копиях каталога задачи; найденное исправление записывается атомарно в настоящий `workspace/mylib.py` (то же делает `fix_coding` в фазе 2).

### Фаза 2: LLM (через `Model.invoke` из openJiuwen)

Для задач, которые не разобрала фаза 1.

- 2a. Нераспознанные math/data/search задачи группируются по шаблону (`harness/templates.py`). Модель один раз на группу выдаёт JSON-спецификацию, которую исполняют те же исполнители, что и в фазе 1 (`harness/json_route.py`). Один вызов покрывает всю группу.
- 2b. Запасной путь для остальных: синтез программы моделью (`harness/llm_routes.py::solve_with_program`), программа исполняется в песочнице. Для coding: лестница патчей `fix_coding` — qwen3.6-35b-a3b-noreason, затем qwen3.8-27b-noreason, затем qwen3.8-27b с низким reasoning (последний шаг только если награда задачи ≥ 3).

Задачи в фазе 2 упорядочиваются по отношению «награда / оценка стоимости» (`harness/estimator.py`): сначала самые выгодные.

Оценка стоимости до вызова (`harness/estimator.py`): длина контекста в символах делится на 3 (символов на токен), промпт взвешивается с коэффициентом 1/10, как в учёте бюджета, и добавляется базовая константа маршрута (JSON-спецификация 80, программа 120, coding 400 токенов на ответ модели). Для coding контекст — `mylib.py` + тесты + 2000 символов запаса; для программы — инструкция + описание workspace. Константы подобраны по тренировочным прогонам (см. «Результаты»).

## Расход токенов

`harness/budget.py`, `TokenLedger`: учёт идёт по ответу прокси. Списываются completion-токены + prompt/10. Для вызова, закончившегося таймаутом, ответом 5xx или оборванным соединением, фиксированно списывается 1500 токенов (`TIMEOUT_CHARGE`). 1% бюджета держится в резерве. Уже записанные ответы остаются на диске независимо от бюджета. Параллельность LLM-вызовов — 3 по умолчанию (потолок аккаунта у dev-провайдера; финальный прокси допускает до 5, меняется переменной `HARNESS_LLM_CONCURRENCY`), таймаут вызова 180 с. Общий дедлайн 3300 с, новые юниты не стартуют за 150 с до него.

## Невыполнимые задачи

Если ответа не существует (человека или компании нет в базе, деление на 0 при разбиении, отсутствует файл или колонка), задача считается невыполнимой: `answer.txt` не создаётся. Если задачу признала невыполнимой фаза 1, токены на неё не тратятся; если это сделала модельная программа с `IMPOSSIBLE`, токены на вызов модели уже потрачены. Такой вывод делает фаза 1 по результату исполнения спецификации, либо программа, написанная моделью в пути 2b, если она напечатала последней строкой `IMPOSSIBLE` (в промпте модели это разрешено, когда ответа по данным нет).

Кто и когда признаёт задачу невыполнимой:
- Фаза 1: по результату исполнения спецификации (0 токенов).
- coding: противоречивые видимые тесты (один вызов с двумя разными ожидаемыми значениями, `coding_solver.contradictory_tests`); проверяется только после неудачного ремонта, 0 токенов.
- 2a (JSON-спецификация модели): окончательно принимается только `solved`. `infeasible` из 2a окончательный лишь для вердиктов, не зависящих от разбора моделью: деление на ноль и отсутствие начальной сущности в базе знаний. Любой другой `infeasible` (выдуманное поле, неверное имя файла, иная папка базы) считается `unparsed`, и задачу пробует путь 2b.
- 2b: программа модели с `IMPOSSIBLE`.

## Траектории

Один файл `trajectory.jsonl` в `HARNESS_LOG_DIR` (по умолчанию `/tmp/harness`): события всех задач в порядке выполнения, идентификатор задачи указан в каждом событии (одна запись на единицу работы: фаза, `task_id`, статус, приращение расхода токенов, затраченное время, примечание; пишется планировщиком `scheduler.py`).

## Результаты

Тренировочные наборы создаёт `tools.gen_tasks` (100 задач, `--infeasible 0.2 --novel 0.2`). Прогон: Docker по команде жюри, `BUDGET=100000`, реальная модель. Сводные траектории: `docs/trajectories/2026-11-08-train.jsonl` (поле `run` отличает прогоны). Генератор делает 20 % формулировок «вне грамматик» (они нарочно уходят в фазу 2) и 20 % невыполнимых задач, поэтому цифры фазы 1 на нём не доказывают точность на задачах организаторов.

| Прогон | score / max | math | data | search | coding | токены | время |
|---|---|---|---|---|---|---|---|
| seed 7, до настройки | 198 / 211 | 20/20 | 18/19 | 21/22 | 17/19 | 8448 | 93 с |
| seed 8, до настройки | 220 / 240 | 18/21 | 17/19 | 20/20 | 19/20 | 8264 | 106 с |
| seed 8, после настройки | 228 / 240 | 18/21 | 19/19 | 20/20 | 19/20 | 1445 | 25 с |

Ячейки по типам: верно / выполнимых задач типа. Невыполнимые задачи в score не входят: у 20 из 100 нет ответа, `answer.txt` не создан у 11 (seed 7), 14 (seed 8 до) и 14 (seed 8 после). Остальные получили ответ по принятому правилу (неизвестный продукт даёт 0), штрафа за них нет.

Что изменила настройка:
- Потолок аккаунта у провайдера: 3 одновременных запроса на все ключи, при 5 приходил 429 и вызов проваливался после 14 с ожидания. `LLM_CONCURRENCY` 5 → 3, задержки повтора 429 теперь 2, 4, 8, 16, 30 с.
- Программа модели для data_analysis/search получала в задании «запиши ответ в answer.txt» и писала файл вместо `print`; промпт теперь запрещает писать файлы (задача стоила 1096 токенов и не решалась, теперь 120).
- Противоречивые видимые тесты (один и тот же вызов с двумя разными ожидаемыми значениями) определяются без модели как `infeasible`: раньше модель подделывала результат (объект с `__eq__`, счётчик вызовов) и тратила 6300 из 8448 токенов seed 7.
- `CODING_BASE` оценки стоимости 200 → 400 (наблюдалось 165–2731 токенов на coding-задачу фазы 2; доказательная база слабая, на порядок ROI при бюджете 100000 не влияет).

Известные остатки: coding-задачи, где несколько однотокенных исправлений проходят единственный видимый тест, а скрытые ловят неверное (1 из 20 на каждом наборе); novel-формулировки вроде «one quarter of the stock is moved» модель переводит в JSON неверно (формат операций не выражает «остаток после изъятия четверти»).

## Локальная разработка

```bash
pip install -r requirements.txt -r requirements-dev.txt
python -m pytest tests
python -m tools.gen_tasks --help
python -m tools.evaluate --run <каталог с задачами и answer.txt>
```
