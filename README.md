# SysCall harness (openJiuwen Challenge 2026)

Харнесс решает задачи четырёх типов (math, data_analysis, search, coding) и для каждой выполнимой пишет `answer.txt`. Большую часть задач он решает детерминированно, без обращений к LLM; модель вызывается только для того, что не удалось разобрать правилами. Вызовы модели идут через `openjiuwen==0.1.19` (`Model.invoke`, провайдер OpenAI-совместимый, `harness/llm.py`); решатели, планировщик и учёт токенов написаны командой.

## Словарь

- **Фаза 1** — решатели без модели (0 токенов). **Фаза 2** — всё, что фаза 1 не решила, с вызовами модели: **2a** (JSON-спецификация на группу однотипных задач), **2c** (арбитраж coding), **2b** (программа или патч от модели на отдельную задачу). Порядок: 2a, 2c, 2b, повторный проход, финальный REASON-проход, подтверждение 2a, 2d, аудит соперничающих форм (раунд 14).
- **Юнит** — одна единица работы фазы 2 (группа 2a, батч 2a, арбитраж 2c или задача 2b); планировщик упорядочивает и запускает юниты.
- **Статусы задачи**: `solved` (ответ записан), `infeasible` (ответа не существует, `answer.txt` не создаётся; если задачу признала невыполнимой фаза 2, на диске может остаться записанный раньше запасной ответ), `unparsed` (решить не удалось; ответа нет, либо только запасной).
- **Запасной ответ (best guess)** — лучшее предположение, которое решатель отдаёт вместе с `unparsed`, когда надёжно решить нельзя. Он пишется на диск сразу и заменяется, если позже найдётся настоящий ответ.
- **Модели** (`harness/config.py`): `MODEL_FAST` = qwen3.8-27b-noreason, `MODEL_ALT` = qwen3.6-35b-a3b-noreason, `MODEL_REASON` = qwen3.8-27b (с `reasoning_effort=low`).
- **Расход** — completion-токены + prompt/10 (рассуждения входят в completion).

## Формат задач

Каталог задач содержит каталоги вида `<task_id>/` (примеры организаторов лежат в `tests/fixtures/examples/`):
- `task.json`: `task_id`, `task_type`, `instruction`, `reward` (баллы за задачу), `check` (`exact_int`, `exact_str` или `unittest`). В примерах есть ещё `expected`; по FAQ от 7 ноября в финальном наборе его уберут; харнесс его не читает.
- `workspace/` (если есть): для data_analysis `sales.csv`; для search папка `kb/` с markdown-файлами о людях и компаниях (поля Born, Employer, Mentor, Founded, Headquarters); для coding `mylib.py` и `test_mylib.py`. У math рабочего каталога нет.
- Ответ — файл `answer.txt` рядом с `task.json`; для coding это слово `DONE`, а исправление записывается в `workspace/mylib.py`.

Харнесс пропускает каталоги `__MACOSX` и начинающиеся с точки, допускает вложенность `каталог/каталог/<задачи>`, читает `task.json` с BOM; без числового `reward` берёт 1.0.

Что сказали организаторы 11 ноября: задачи на английском, русский может встречаться только в комментариях; формулировки будут другими, чем в примерах, в тестах будут подвохи, задачи одной категории не обязательно однотипны; бюджет всегда 100000; штрафа за ответ на невыполнимую задачу нет; скрытые тесты coding заменяют видимый файл и, скорее всего, ловят ошибки, которых видимые тесты не видят.

## Сборка и запуск

Команда жюри (из регламента; в регламенте у `docker build` нет контекста, здесь добавлена точка):

```bash
mkdir -p "$OUT" && chmod 777 "$OUT"

docker build -t "hack:latest" . && \
timeout -k 1000s 1h docker run --rm --name "run-${TEAM}" \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  "hack:latest" \
  /app/run_agent.py --tasks-dir /data/tasks
```

`TEAM` — имя команды, `TASKS` — каталог с задачами на хосте, `OUT` — каталог на хосте (по ответам организаторов 2026-11-09 `OUT` устарел: считается `answer.txt`), `hack-net` — сеть, которую создаёт жюри. `docker build` выполняется из корня репозитория. В контейнер попадают только `LLM_BASE_URL`, `LLM_API_KEY` и `TASKS` как каталог `/data/tasks`; `BUDGET` и `OUT` не передаются, поэтому в прогоне жюри действует бюджет по умолчанию 100000 (по FAQ организаторов от 7 ноября: «ориентируйтесь на бюджет 100K», «BUDGET=100000»; в регламенте числа нет; если настоящий бюджет меньше, харнесс этого не узнает, и прокси перестанет отвечать раньше, чем его счётчик исчерпается — см. «Бюджет и защита от обрыва»), а результат — только `answer.txt` в каталоге каждой задачи, у которой есть ответ (требование регламента «создать answer.txt в каталоге каждой задачи» относится к ним; для невыполнимой задачи FAQ от 7 ноября говорит: «не создавайте файл»). Код выхода всегда 0, в том числе при пустом каталоге задач: тогда харнесс молча находит ноль задач.

**Локальный запуск без Docker и без ключа** (Python 3.11+; работает только фаза 1):

```bash
pip install -r requirements.txt -r requirements-dev.txt
python -m tools.gen_tasks --out /tmp/set --n 100 --seed 1    # /tmp/set/tasks и /tmp/set/hidden
HARNESS_LOG_DIR=/tmp/set/log python run_agent.py --tasks-dir /tmp/set/tasks
python -m tools.evaluate --run /tmp/set --log /tmp/set/log/trajectory.jsonl
```

**Локальный запуск в Docker с настоящим прокси** (сверху вниз; нужны Python 3.11+ и Docker). Адрес и ключ прокси выдают организаторы; их кладут в окружение хоста и никогда не коммитят:

```bash
pip install -r requirements.txt                       # нужен для gen_tasks
python -m tools.gen_tasks --out set --n 100 --seed 1  # сначала набор: создаёт set/tasks и set/hidden
export LLM_BASE_URL=<адрес прокси>  LLM_API_KEY=<ключ>
docker network create hack-net
docker build -t hack:latest .
docker run --rm --network hack-net -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET=100000   -e HARNESS_LOG_DIR=/data/tasks/_harness_log   -v "$PWD/set/tasks:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp   --cap-drop ALL --security-opt no-new-privileges --cpus 8 --memory 16g --pids-limit 512   --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
python -m tools.evaluate --run set --log set/tasks/_harness_log/trajectory.jsonl
```

Если смонтированный каталог пуст, харнесс молча выходит с кодом 0. Предупреждение «skipping task dir _harness_log» в stderr безвредно. `tests/chaos/fakeproxy.py` — подставной прокси для проверки без ключа (`python -m pytest -m chaos`).

Образ и сборка: `python:3.11.11-slim-bookworm`, зависимости закреплены в `requirements.txt` (`openjiuwen==0.1.19` и транзитивные версии, собрано под linux x86_64), при запуске ничего не скачивается. Локально собранный образ `hack:latest` весит 1,42 ГБ по `docker images` (лимит 4 ГБ), файлы репозитория занимают около 1 МБ (лимит 100 МБ).

Раскладка: `run_agent.py` (точка входа), `harness/` (`solvers/` — фаза 1; `json_route.py`, `arbitrate.py`, `llm_routes.py` — фаза 2; `llm.py` — клиент модели; `oj_agent.py` — агент и инструменты openJiuwen; `budget.py`, `estimator.py`, `scheduler.py`), `tools/` (генератор задач, оценщик, стенды), `tests/`, `docs/trajectories/`.

### Переменные окружения

- `LLM_BASE_URL`, `LLM_API_KEY` — прокси организаторов. Если не заданы, работает только фаза 1.
- `BUDGET` — бюджет токенов (умолчание 100000). `HARNESS_LOG_DIR` — каталог траекторий и логов (умолчание `<tempdir>/harness`, то есть `/tmp/harness`; на `tmpfs` с `--rm` он исчезает после прогона).
- `TASKS` — запасной каталог задач; `OUT` или `--out` — необязательный файл `{task_id: answer}`, который переписывается после каждого ответа. Он не нужен, считается `answer.txt`. Каталог задач берётся из `--tasks-dir`, позиционного аргумента, `TASKS`, `/data/tasks` (первый, где есть `task.json`); выбор пишется в stderr.
- Ручки времени и параллельности, все необязательны; пустое, нечисловое, отрицательное или бесконечное значение заменяется умолчанием с одним предупреждением (кроме `HARNESS_LLM_CONCURRENCY`: она заменяется молча): `HARNESS_LLM_TIMEOUT` — таймаут вызова модели, с (180); `HARNESS_DEADLINE_S` — общий дедлайн, с (3300; лимит жюри 3600); `HARNESS_STOP_NEW_BEFORE_DEADLINE_S` — за сколько секунд до дедлайна новые юниты не стартуют (150); `HARNESS_RETRY_DELAYS` — паузы повтора на 429 и при сбоях прокси, с, через запятую (`2,4,8,16,30`); `HARNESS_PROXY_DEAD_S` — сколько секунд без единого успешного ответа считать прокси мёртвым (по умолчанию равно дедлайну); `HARNESS_PHASE1_TIMEOUT_CODING` и `HARNESS_PHASE1_TIMEOUT_DEFAULT` — таймаут фазы 1 на coding-задачу и на остальные, с (100 и 15); `HARNESS_LLM_CONCURRENCY` — одновременных вызовов модели (3: потолок аккаунта у dev-провайдера, финальный прокси допускает до 5); `HARNESS_BATCH_2A` — батчинг групп в 2a (включён, `0`/`false` отключает). `HARNESS_CONFIRM_2A` — подтверждение ответов 2a для data голосованием независимых программ (по умолчанию включено, `0` отключает). `HARNESS_VERIFY_CODING` — независимая проверка зелёных одиночных coding-фиксов, этап 2d (включена, `0`/`false` отключает; около 60 единиц на проверенную задачу). `HARNESS_REASON_MATH` — math в 2b сначала решает `MODEL_REASON` (включено; `0` даёт ровно поведение раунда 9: ни REASON в 2b math, ни голосов по math). `HARNESS_CONFIRM_MATH` — подтверждение ответов 2a для math голосами REASON, FAST и ALT (по умолчанию выключено; работает только вместе с `HARNESS_REASON_MATH`). `HARNESS_MINE_TEXTS` — выученные тексты функций для фазы 1 coding (раунд 11, см. «Фаза 1»; по умолчанию включено, `0`/`false` отключает: фаза 1 coding идёт без выученных текстов, а правила невыполнимости и restart для текстов из примеров организаторов действуют и тогда). `HARNESS_AUDIT_FORMS` — аудит соперничающих зелёных форм функций coding в конце прогона (раунд 14, см. «Фаза 2»; по умолчанию включён, `0`/`false` даёт ровно поведение раунда 13). `HARNESS_OJ_AGENT` — харнесс работает как агент openJiuwen (раунд 16, см. «Где используется openJiuwen»; по умолчанию включено, `0`/`false`/`no`/`off` запускает планировщик напрямую, без слоя агента). `HARNESS_PROSE_AGREE` — согласие попыток на прозаической базе знаний (раунд 17, см. «Фаза 2»; по умолчанию включено, `0`/`false` оставляет одну попытку FAST, как в раунде 16, но правило о константе в цепочке действует и тогда). `HARNESS_REVIEW_CODING` — ревью решённых coding-файлов двумя моделями в самом конце прогона (раунд 18, см. «Фаза 2»; по умолчанию включено, `0`/`false` даёт ровно поведение раунда 17). Раунд 20: `HARNESS_MINIMAL_PATCH` — сокращение зелёного патча лестницы coding, возврат встроенного вызова своей функции (см. «Фаза 2»; по умолчанию включено, `0`/`false` даёт ровно поведение раунда 19); `HARNESS_MINIMAL_DEFS` — проход по целым определениям в том же сокращении (по умолчанию выключен, `1` включает; работает только вместе с `HARNESS_MINIMAL_PATCH`). Раунд 21, всё по умолчанию включено, `0`/`false` даёт поведение раунда 20 для своей части: `HARNESS_REVIEW_PROBES` — шире пробные входы ревью и подтверждённое зависание; `HARNESS_CONFTEST` — фикстуры `conftest.py` в замене pytest; `HARNESS_RICH_PREVIEW` — содержимое SQLite, xlsx, zip, gzip и структура JSON в подсказке 2b; `HARNESS_CODING_RESCUE` — запасной маршрут coding целыми файлами (см. «Фаза 2»). Раунд 22, по умолчанию включено (кроме `HARNESS_BIG_WS`), `0`/`false` даёт поведение раунда 21 для своей части: `HARNESS_FULL_SMALL` — короткий текстовый документ (до 1500 байт, не таблица, лог или код), обрезанный превью, показывается в подсказке 2b целиком (не больше 3000 байт сверх обычных 4096); `HARNESS_KB_EXTRAS` — подсказка маршрута базы знаний с полями показывает и текст страниц без полей, и первые строки файлов вне `kb/`; `HARNESS_REVIEW_RETRY` — ответ ревью coding, упёршийся в лимит вывода, переспрашивается один раз с лимитом 1400 токенов; `HARNESS_REVIEW_LONG` — пробы ревью подают числовые значения параметрам, которые видимые тесты оставляют по умолчанию (строки не подаются: произвольная строка выходит за допустимые значения параметра-перечисления и делает верную функцию «неверной»); `HARNESS_BIG_WS` — рабочий каталог больше 100 МБ подставляется программе модели ссылками, а не копией в `/tmp` (по умолчанию выключено: через ссылки программа модели может изменить исходные данные задачи; `1` включает только для заведомо безопасных наборов). Раунд 23: `HARNESS_PRIO_CAL` — порядок юнитов 2b по награде на ожидаемую цену с поправкой оценки по типу задачи (coding ×0,75, data ×1,3, math ×2,4, search ×1,6; меняется только очередь, оценка для проверки бюджета прежняя; по умолчанию включено, `0`/`false` возвращает порядок раунда 22).
- Доказательство «тесты импортируют несуществующий модуль» (раунд 14, `coding_solver.missing_test_import`) реализовано, но выключено константой `coding_solver.MISSING_IMPORT_PROOF = False`; переменной окружения у него нет. Причина: скрытые тесты заменяют видимый файл и могут этот модуль не импортировать, тогда задача выполнима, а экономия всего около 670 единиц на задачу.

### Запись ответов

Каждый ответ пишется сразу после решения: временный файл рядом, `fsync`, `os.replace`; если каталог не позволяет создавать файлы, пишется напрямую в `answer.txt`. В `/app` ничего не пишется. Каталог задач должен быть доступен на запись для root в контейнере (организаторы 2026-11-09 подтвердили, что будет); при недоступности в stderr печатается `TASKS DIR NOT WRITABLE: uid=… owner=… mode=…`. В конце на stdout выводится `solved=… infeasible=… unparsed=… spent=…`.

## Где используется openJiuwen

Версия `openjiuwen==0.1.19` (закреплена в `requirements.txt`).
- **Агент.** Точка входа — `HarnessAgent(BaseAgent)` с `AgentCard` в `harness/oj_agent.py`: `run_agent.py` строит агента и вызывает его `invoke`, а тот решает весь набор задач (`scheduler.run` в рабочем потоке: у планировщика свой цикл событий).
- **Модель.** Все вызовы модели идут через `Model` openJiuwen (`harness/llm.py`, OpenAI-совместимый клиент к `LLM_BASE_URL`).
- **Инструменты.** То, что харнесс исполняет для модели, оформлено как инструменты openJiuwen (`LocalFunction` с `ToolCard`, зарегистрированы в `ability_manager` агента): `run_program` — программа модели в 2b и финальном проходе REASON, во временной копии каталога; `run_tests` — прогон тестов против кандидата в лестнице coding. Результат инструмента — тот же объект, что вернула функция. Не все прогоны идут через инструменты: проба константы в прозаической базе и прогоны арбитража 2c/2d вызывают функции напрямую.
- **Почему планировщик свой.** Главная задача кейса — контроль бюджета: фаза 1 решает без модели за 0 токенов, дальше юниты идут по `reward / оценка` с резервом под каждый вызов (см. «Оценка расхода», «Бюджет»). Цикл «модель сама выбирает инструмент» тратил бы токены на каждый шаг, поэтому решения принимает код харнесса, а openJiuwen даёт агента, модель и инструменты.
- **Страховка.** Слой не построился — `scheduler.run` вызывается напрямую; инструмент упал до вызова своей функции — обычный вызов функции. Если функция уже отработала, её результат или её собственная ошибка возвращаются как есть: юнит никогда не исполняется дважды, и набор никогда не решается второй раз. `HARNESS_OJ_AGENT=0` выключает слой целиком.
- **Логи и сеть.** Логи openJiuwen пишутся в `HARNESS_LOG_DIR/openjiuwen-logs` (уровень WARNING, только в файлы; процесс переходит в `HARNESS_LOG_DIR`, потому что `/app` в прогоне жюри только для чтения). Слой не ходит в сеть дальше `LLM_BASE_URL` (проверено `--network none`). Цена: 3–7 с на импорт и сборку, 0 единиц.

## Архитектура

### Фаза 1: решатели без модели

`harness/solvers/*`, 8 процессов (`spawn`), жёсткий таймаут на задачу: 15 с, для coding 100 с; coding-решатель останавливается сам за 15 с до этого (85 с), чтобы успеть записать предварительный ответ.
- **math**: разбор предложения по грамматике шаблонов и вычисление шагами-выражениями. Отрицательный запас ответом не считается (см. запасные ответы). С раунда 11 количество, названное без числа (`several`, `some`), даёт `infeasible` (см. «Невыполнимые задачи»).
- **data_analysis**: разбор вопроса в запрос к CSV: суммы, количество заказов, выручка (в том числе с определением в скобках: «revenue (units * price)», «(units x price)», «(units times price)», «(units multiplied by price)» и обратный порядок «price … units»), средние, `top_product_*` и `top_region_*`, `max_units`/`min_units`, округление «rounded to N decimal places». Свободный разбор принимает только вопросы, где неизвестных слов нет; любой неизвестный квалификатор («excluding», «first 3 months», «per unit») даёт `unparsed`, а не угаданный ответ. С раунда 11 фильтр по значению, которого нет в файле, и месяц вне 1..12 могут давать `infeasible` (см. «Невыполнимые задачи»).
- **search**: разбор цепочки запросов к базе знаний (человек → работодатель → город штаб-квартиры и т. п.). Поле, не подходящее по виду сущности (Founded у человека), и обратные связи («кого наставляет X») не угадываются.
- **coding**: ремонт кода однотокенными мутациями; кандидаты проверяются на видимых тестах во временной копии каталога; найденное исправление записывается в настоящий `workspace/mylib.py`. Если подходящих исправлений несколько, решатель группирует их по поведению на видимых вызовах и выбирает по правилу ничьей (`coding_solver._edit_rank`: разворот сравнения лучше смены строгости, она лучше отрицания; константа, сдвинутая к нулю, лучше сдвинутой от нуля; исправление, убирающее пустую операцию вроде `x * 1`, лучше создающего её). Задача получает предварительный ответ `DONE` и идёт в арбитраж 2c. Перебор ограничен (400 мутантов, 9 вариантов на функцию) и касается только функций верхнего уровня.
  - **Известный текст до перебора** (раунд 10). Каждая функция, которую вызывает красный тест и чьё имя есть среди функций из примеров организаторов (`reverse_words`, `total`, `maximum`, `average`, `first_n`, `count_even`), по одной заменяется известным правильным текстом. Условия: функция верхнего уровня, без декораторов, с теми же параметрами; та же форма (`coding_solver._same_shape`: те же виды операторов, поэтому docstring, лишний `if` или ветка не проходят; вызываемые имена — подмножество имён известного текста и `sorted/max/min/len/sum/reversed`, поэтому `abs` или `round` не проходят; не больше защит-выражений, чем в известном тексте: `… if xs else None`, `x or 0`, `and` с операндом, не являющимся сравнением значений, вроде `xs and xs[0]` или `x is not None and …`); множество красных тестов строго уменьшается, и ни один зелёный не краснеет. Лишнее условие-сравнение (`x % 2 == 0 and x > 2`) защитой не считается и заменяется. Дальше перебор мутаций продолжается от результата. Если время кончилось, принятая замена остаётся частичным ремонтом. Результат, совпавший с известным текстом, окончателен сразу (`repaired by mutation, canonical`), без 2c и 2d; если перебор потом снова изменил заменённую функцию, подсказка 2d показывает настоящий исходный текст, а не известный. Принятые остаточные риски (та же форма, защита теряется при замене): `split(' ')` заменяется на `split()`; защита, записанная через `max`/`min` (`xs[:max(n, 0) + 1]`, `sum(xs) / max(len(xs) - 1, 1)`); второе условие `if` в генераторе списка. В тестах неоднозначности (`test_arbitrate.py`, `test_coding_solver.py`, `test_verify_coding.py`) функция переименована из `count_even` в `count_evens`, чтобы их фикстуры не попадали под известный текст. Замер: матрица из 55 правдоподобных багов (`scripts3/coding_matrix.py`, в 3 из них видимый тест уже зелёный) — 52/52 `canonical` (до раунда 10 29/52); live9 coding 17/17 при 0 единиц.
  - **Известный текст и в зелёном состоянии** (раунд 12, `coding_solver._restore_known`). Когда видимые тесты зелёные (сразу или после ремонта), каждая функция с именем из примеров организаторов, записанная иначе, но той же формы (те же условия, что у подстановки раунда 10, включая `_same_shape`), по одной заменяется известным текстом из примеров (`_EXAMPLE_TEXTS`; выученные из набора тексты не участвуют). Замена остаётся, только если весь видимый прогон остаётся зелёным; ошибка или нехватка времени оставляют сделанное. Так закрыт подвох «ошибка, которую видимый assert не ловит» (`best = 0`, `sum(xs) // len(xs)`): на наборе v5 coding 16/20 → 20/20, матрица из 55 ошибок 53 → 55, на 225 coding-задачах прежних наборов исход не изменился. Остаточный риск (оценка ревью около 1 % coding-задач): правильная по смыслу задачи функция той же формы, которую видимый тест не отличает от известного текста, заменяется им — например защита через `max`/`min` (`xs[:max(n, 0)]`, `sum(xs) / max(len(xs), 1)`), `split(' ')`, лишнее условие `and x > 0`.
  - **Выученные тексты** (раунд 11, `coding_solver.mine_known_texts`, `HARNESS_MINE_TEXTS`). Если в наборе не меньше 3 coding-задач, до фазы 1 харнесс в родительском процессе по очереди прогоняет видимые тесты каждой coding-задачи: один прогон на задачу во временной копии каталога, до 10 с на прогон и не больше `min(60 с, 10 % времени до дедлайна)` на всё, перекрёстная проверка включена (плюс до ~5 с на снятие последнего прогона). Прогон идёт тем же путём, что в фазе 1: `run_python`, окружение без `LLM_API_KEY`, `LLM_BASE_URL` и `BUDGET`, те же rlimits. Кандидат — функция верхнего уровня без декораторов, определённая один раз, самодостаточная (не читает других имён модуля, без `global`/`nonlocal`), с именем не из примеров. Задача голосует за текст функции (форма по AST), если все её непропущенные тесты, вызывающие эту функцию, зелёные. Задачи с одинаковыми по AST `mylib.py` и тестами считаются один раз. Прогон с `<timeout>`/`<unknown>` или с красным тестом, который нельзя отнести к функциям, не голосует.
    - Текст принимается при ≥ 2 голосах, если у него вдвое больше голосов, чем у всех соперничающих зелёных форм вместе, и он прошёл перекрёстную проверку. Проверка подставляет текст в каждую задачу, где функция красная сама по себе (её красный тест использует только её и окончательные тексты примеров, стоящие как есть) и той же формы; если там остаётся красным такой тест (или стоит этот же текст и он красный), текст отклоняется. Нехватка времени на проверку тоже означает отказ.
    - **Окончательный** текст: ≥ 3 голосов и 0 против. Если время mining кончилось раньше, чем прогнаны все задачи, или урезанный остатком таймаут оставил прогон без результата, окончательных текстов нет: все принятые остаются слабыми (не прогнанная задача могла голосовать против). Окончательный текст работает как текст из примеров: даёт `canonical` (без 2c и 2d) и может доказать `infeasible` (см. «Невыполнимые задачи»). **Слабый** текст подставляется только после окончательных и только при строгом уменьшении числа красных тестов. Он не входит в базу подсказок 2c/2d и в `restart` (модель видит настоящий текст функции) и дальше проверяется как ремонт мутацией: `_ambiguity`, затем 2c или 2d.
    - Лог: строка `mined texts of N functions from M coding tasks in X s: […]; final: […]` в логе `harness`. Замер: pool из 25 coding-задач (`scripts4/mk_pool.py … 25 7`) — 25/25 за ~102 единицы (до раунда 11 22/25 за 1804). Время шага 1,5–2 с на 25–30 задач. На 372 coding-задачах без модели (генератор s401–s406, pool, v3, v4) 0 ложных `infeasible` и 0 неверных `canonical`; `scripts4/scan_coding.py` на 585 задачах — 0 срабатываний на выполнимых.
  - **Частичный ремонт и `restart`** (раунд 11). Если перебор оставил красные тесты, предварительный ответ несёт `extra.restart`: исходный `mylib.py` с подставленными окончательными известными текстами, без мутаций и без слабых выученных текстов. С него начинается лестница 2b (см. «Фаза 2»).

**Предварительные ответы.** Ответ, записанный как предварительный (частичный ремонт или неоднозначный выбор), остаётся в `answer.txt`, а задача идёт в фазу 2 за улучшением. Неудачная поздняя попытка его не отзывает.

**Запасные ответы.** Решатель возвращает `unparsed` вместе с запасным ответом, если решить надёжно нельзя: math при отрицательном запасе, data при ничьей за первое место, search при расхождении двух чтений вопроса. Так же поступают 2a и 2b, если ответ и после повтора не прошёл проверку формы (такая догадка `shape_mismatch` занимает только пустое место). Запасной ответ пишется на диск сразу, а не в конце: прогон могут остановить без предупреждения. Он заменяется настоящим ответом. Вердикт `infeasible` фазы 2 его не удаляет (раунд 15). Если вердикт не зависит от модели (`division by zero`, `start entity not found`), задача считается `infeasible` и больше не получает вызовов модели, а запасной ответ остаётся на диске: ответ на невыполнимую задачу не засчитывается и не штрафуется, а если вердикт ошибочен, догадка может принести баллы. IMPOSSIBLE от модели запасной ответ тоже оставляет (и задача остаётся кандидатом финального REASON-прохода): штрафа за неверный ответ нет, а модель называла выполнимые задачи невыполнимыми.

### Фаза 2: модель

Для задач, которые фаза 1 не решила (или решила предварительно).

- **2a.** Нераспознанные math/data/search задачи группируются по шаблону (`harness/templates.py`: числа и имена заменяются слотами). Модель один раз на группу выдаёт JSON-спецификацию (`harness/json_route.py`), её исполняют те же исполнители, что в фазе 1. Для math это `{"start": N, "steps": ["x-{N2}*{N3}", "x-x//4"]}` (шаги вычисляет безопасный AST-вычислитель: только `x`, целые, `+ - * //`); для search `{"entity": "{E1}", "hops": ["Mentor", "Employer", "Headquarters"]}`. Спецификация `{"impossible": true}` разрешена для величин, которых нет в данных; в math она возвращается на любой вопрос, кроме «сколько осталось в конце», и такая задача уходит в 2b. Проценты считаются как `x*N//100`. Расход на группу: обычно один вызов, плюс повтор при битом JSON и один повтор на `MODEL_ALT` при ответе не той формы (`harness/shape.py`: год из 4 цифр, имя, целое) или при числе шагов меньше числа операций в тексте. У search-вопроса, который спрашивает число или да/нет, формы нет и проверка не делается: вопрос начинается с «how many / how much / how old», «what is the (total) number of», «answer yes or no» или с глагола вопроса да/нет (`is/are/does/did/was/were/do/has/have/can/will`; «Can you tell me the year…» и «Do you know who…» вопросом да/нет не считаются и сохраняют форму года или имени, а «Can you tell me whether/if…» считается), либо такая фраза («how many», «number of», «yes or no») стоит в вопросе без явного who/which/where/when/«what city». «The largest (highest, most …) number of …» — выбор сущности, а не счёт: «Which company has the largest number of employees?» сохраняет форму имени. Вопросы, идущие по связи в обратную сторону, в 2a не задаются, а сразу уходят в 2b. Батчинг (группы упорядочены по номеру задачи): до 4 мелких групп одного типа (до 2 задач в каждой) получают спецификации одним вызовом; негодный элемент решается своим вызовом; так же один раз перезапрашивается своим вызовом участник батча, закончивший `unparsed` (кроме обратной связи, `impossible` и `shape_mismatch`). Сырая спецификация каждой группы пишется в лог `harness` на уровне INFO (до 300 символов). Проверка числа шагов в батче (раунд 16, `json_route.hop_count_mismatch`): если в спецификации search из батча число шагов `Mentor` или `Employer` не равно числу слов `mentor`/`mentors`/`mentoring` или `employ…`/`works for`/`payroll` в тексте, спецификация отбрасывается и текст получает свой вызов, как без батча. Слова считаются, только если все они стоят в одном предложении: текст, где цепочка пересказана по шагам и затем задана вопросом, или вступление («trace the mentorship chain») не проверяются; «mentorship» не считается. Ответ на одиночный вызов проверка не трогает. Так закрыт разброс search_0021 в live9: в батче модель изредка копировала лишний `Mentor` у соседнего текста.
- **2c.** Арбитраж неоднозначных coding-задач (`harness/arbitrate.py`): `MODEL_FAST` и `MODEL_ALT` независимо отвечают номером варианта (`max_tokens` 8). Выбор меняется только если обе назвали один и тот же вариант, отличный от детерминированного, и только после полностью зелёного видимого прогона; иначе остаётся детерминированный выбор. Замер раунда 3 на 100 трудных coding-задачах: 92/100 до, 95/100 после (одна модель, без правила ничьей и с ним вместе с согласием двух моделей); цена около 87 токенов на задачу против 43.
- **2b.** Запасной путь. Для math (раунд 10, `HARNESS_REASON_MATH`) сначала один вызов `MODEL_REASON` с просьбой написать программу (`reasoning_effort=low`, 3000 токенов), если выполнены все четыре условия: весь вызов помещается в учёт (оценка задачи + 3000); потрачено меньше 50 % бюджета; до момента, когда новые юниты перестают стартовать, осталось не меньше `HARNESS_LLM_TIMEOUT` + 60 с (иначе юнит отменили бы до программы FAST); задачу ещё не решил REASON (вердикт ставится только по ответу самой модели, не при недоступности или обрезке бюджетом). Ответ REASON нужной формы окончателен. `IMPOSSIBLE` от REASON принимается на веру: программа FAST после него не запускается (REASON 20 из 20 на выполнимых math; на v3 `math_9319` FAST записал ответ невыполнимой задаче), а уже лежащая на диске догадка остаётся (мягкий `infeasible`). Программа FAST запускается, только если REASON не дал вердикта или дал ответ не той формы; такой ответ сначала записывается как догадка `shape_mismatch`, ответ FAST его заменяет, догадка FAST — нет. Замер: llm8 math 28/28 за 3183 единицы (раунд 9: 3208), v3 math 13/14 за 3385. Худший случай: юниты 2b math упорядочены по оценке без учёта 3000 токенов REASON и поэтому идут раньше coding-лестниц и программ search/data. Если до 2b доходит 16 и больше math-задач (например, новые формулировки, от которых отказалась 2a), REASON стартует, пока не потрачено 50 % бюджета, а до трёх вызовов в полёте (около 3,1 тыс. каждый) добавляют ещё около 9 тыс., всего около 59 тыс. Каждый вызов длится до `HARNESS_LLM_TIMEOUT` (180 с) на трёх потоках. Финальный REASON-проход и голоса подтверждения data стоят за тем же порогом 50 % и тогда не получают ничего. Учёт при этом не превышается и дедлайн не срывается (проверка времени и резерв `hold` на каждый вызов); на замеренных наборах до этого далеко. Для math/data/search: программа от `MODEL_FAST` (до двух попыток, вторая с ошибкой первой, `max_tokens` 900: программы search, читающие базу знаний, на 400 обрезались), исполняется отдельным процессом на копии каталога (до 20 с); при ответе не той формы один вызов на `MODEL_ALT`. Для search с каталогом `kb/` база знаний уже загружена в словарь `kb` (заголовок страницы -> {поле: значение}): свой системный промпт, в user-тексте число страниц и по одному примеру страницы каждого вида, а загрузку файлов перед программой добавляет сам harness (программа модели исполняется под именем `<program>`). Нет страницы (`kb[...]`), либо программа напечатала `None`/`unknown`/`n/a`: итог `unparsed` («kb page or field not found») без повтора и без догадки. Страница есть, а спрошенного поля у неё нет (`KbFieldMissing`, раунд 10): один повтор, в котором перечислены существующие поля и подсказано, что обратную связь («кого наставляет X», «кто работает в X») ищут перебором `kb.items()` с `.get()`; повторный промах даёт прежний итог «not found». После повтора по полю догадка не сохраняется ни при каком исходе (модель недоступна, повтор формы исчерпан, конец попыток). В системном промпте правило: отвечать только спрошенным полем, а если у сущности такого поля нет, печатать `IMPOSSIBLE`; обратная связь и подсчёт отсутствующим полем не считаются. Напечатанные dict, list, tuple и представления словаря отвергаются (один повтор с просьбой напечатать одно значение) и никогда не становятся догадкой. Программа, печатающая голую константу (`print(340)`, число посчитано «в уме»), отвергается без запуска, один повтор с причиной. Если модель недоступна, берётся следующая (`chat_or_alt`). Для coding лестница патчей: `MODEL_FAST` (400 токенов), `MODEL_ALT` (600), `MODEL_REASON` (3000, выполняется при награде ≥ 3 или если осталось больше половины бюджета); следующая ступень стартует от частичного результата предыдущей. С раунда 11, если фаза 1 оставила частичный ремонт с `extra.restart`, первым делается один вызов `MODEL_FAST` (400) на весь ремонт от `restart`, то есть от файла до мутаций: мутации частичного ремонта выбраны по одному видимому assert каждая, и их никто не проверял. Зелёный результат принимается (нота `patched by … from the file before mutations`). Иначе лестница идёт как раньше, от частичного файла. `ModelFailing` на этом вызове ведёт на лестницу. - **Сокращение зелёного патча модели** (раунд 20, `HARNESS_MINIMAL_PATCH`; `llm_routes._write_and_cut`, `_cut_back`, `_line_restores`, `_inlined`). Лестница останавливается на первом патче, при котором видимые тесты зелёные. Модель при этом может переписать больше, чем нужно тестам, и сломать то, что видимые тесты не проверяют. Зелёный патч сначала записывается на диск, поэтому отмена юнита по дедлайну во время сокращения не теряет решённую задачу. Затем патч сравнивается с исходным файлом задачи (`restart`, если фаза 1 оставила частичный ремонт; иначе файл до лестницы). В каждом определении, которое модель изменила, строка блока, переписанного моделью (`replace` у difflib), по одной получает обратно самую похожую строку исходного блока (тот же отступ, сходство от 0,5). Это делается, только если исходная строка — голый вызов функции или метода, определённых в том же файле, то есть модель встроила вызов вместо него, и только если видимые тесты остаются зелёными. Условия и исключения: строка модели сама не вызывает ту же функцию (иначе это исправление аргументов: `notify(log, order_id, who)`); у вызова метода получатель — простое имя (`self`, `other`, параметр; `self.tags.remove(t)` — метод множества, а не свой); у получателя, отличного от `self`, имя метода не совпадает с методом list/dict/set/str; ни одна строка тела вызываемой функции, действующая на `self.`, не стоит уже на этом получателе в другом месте определения (модель встроила вызов целиком, и возврат вызова повторил бы его действие). Условие, заголовок блока или другая строка обратно не возвращаются: смесь блока модели со старым условием (deep19 coding_9707, `if left <= 0:` → `if left < 0:`) не совпадает ни с одной версией и прячет ошибку, которую видимые тесты не ловят. Определения, добавленные моделью, остаются. Ревью и аудит идут уже на сокращённом файле. Нота получает «, cut back to the original text: [...]». Время: до 20 с лишних прогонов тестов на задачу (`MINIMAL_PATCH_S`; проверяется перед каждым прогоном, поэтому предел — 20 с плюс один прогон), 0 единиц. Повод: far8 coding_8001. Видимый тест требует изменить `transfer` (в истории отправителя только `("transfer", n)`), а модель вместе с этим записала `other.balance += amount` вместо `other.deposit(amount)`, и у получателя пропадала запись `("deposit", n)`. Сокращение возвращает `other.deposit(amount)`. Проход по целым определениям (`HARNESS_MINIMAL_DEFS`, по умолчанию выключен) перед этим возвращает исходный текст каждому изменённому определению, если видимые тесты остаются зелёными. Выключен он потому, что на записанных прогонах (far8, sil9, deep19, trap1, около 40 зелёных патчей) не сработал ни разу, а теряет тихое исправление в другом определении: модель починила видимую ошибку в `spread` и заодно `//` → `/` в `mean`, видимый тест `mean([2, 4]) == 3` зелёный и на старом тексте, и проход вернул бы ошибку. Замер без модели (зелёные патчи записанных прогонов, замены ревью и аудита защищены): far8 coding_8001 из красной по скрытым тестам становится зелёной в 8 прогонах из 8, на sil9 (4 прогона), deep19 и trap1 (8 прогонов) ничего не меняется.
- **Запасной маршрут coding** (раунд 21, `HARNESS_CODING_RESCUE`; `harness/rescue.py`). Лестница чинит один Python-файл по одному файлу тестов, и задача другого устройства раньше оставалась без ответа и без вызова. Маршрут срабатывает, когда файла для ремонта ещё нет (`solve.py` по описанию), нет файла тестов (тесты — примеры в докстрингах, `python -m doctest` из текста задачи), код не на Python, или когда все ступени лестницы ответили, тесты остались красными, а в каталоге есть другие исходники (ошибка в модуле, который тесты не импортируют; `.venv`, `node_modules` и скрытые каталоги не считаются). Сначала запускаются проверки, которые можно выполнить здесь: если они уже зелёные — `DONE` без вызова и без записи. Модель (`MODEL_FAST`, затем `MODEL_ALT`, 1800 токенов) видит текст задачи и файлы каталога и возвращает целые файлы в блоках `FILE … END FILE`. Вызова нет, если показанного целиком кода больше 4500 символов (ответ не уместится), если остаток бюджета не вмещает целый ответ, и после `ProxyDown`. Писать можно: новые файлы и существующие файлы кода (`.py`, `.js`, `.ts`, `.go`, `.java`, `.rb`, `.c`, `.h`, `.cpp`, `.rs`, `.sh`), показанные целиком. Нельзя никогда: тестовые файлы, конфигурацию прогона (`pytest.ini`, `setup.cfg`, `tox.ini`, `pyproject.toml`, `conftest.py`, `sitecustomize.py`, `package.json`, `run_tests.py` и т. п., `*.pth`), каталоги `testdata/`, `fixtures/`, `expected/`; существующие файлы данных; новый файл данных, имя которого есть в каком-нибудь файле кода (тестах или помощнике вроде `loader.py`); модуль без `def` и `class`, который импортирует код (`expected.py` с `TOTAL = 7`); пути за пределы каталога. Для doctest новый текст должен сохранить все примеры исходного файла (ввод и ожидаемый вывод) и иметь хотя бы один, иначе он красный. Ответ сохраняется, если проверки, которые можно запустить, зелёные, или если запускать нечего (другой язык). Красный ответ не сохраняется.

Иначе третья попытка — программа `MODEL_REASON`, побеждает ответ, общий для двух попыток; без большинства — ответ REASON, затем FAST, затем ALT. Голосом не считаются: упавшая программа, `IMPOSSIBLE`, заглушка, ответ не той формы и ответ ALT, который отдали веса FAST (ALT был недоступен). Константа REASON (голое число или `print` константы) на вопросе про счёт, выбор или цепочку — не голос; если больше никто не ответил, она пишется догадкой (`best_guess`), задача остаётся открытой для финального прохода. Любая первая попытка без ответа (упавшая программа, пустой вывод, ненайденная страница или поле, `IMPOSSIBLE`, исключение маршрута) идёт дальше к ALT и REASON; останавливают только недоступный прокси (повторный проход) и обрезка бюджетом. FAST и ALT, оба напечатавшие `IMPOSSIBLE`, — согласие без REASON. Из совпавших написаний пишется чистое: без закрывающей точки и кавычек, с прямым апострофом, целое без `.0`; точка сокращения (Jr., Inc., Co., U.S.) остаётся. Ответ FAST пишется на диск до лишних попыток, ответ ALT — до REASON, когда у FAST ответа нет. Каждая попытка идёт через тот же клиент и учёт; новая попытка не стартует после 50 % бюджета или после остановки новых юнитов, REASON — ещё и без целого вызова в учёте и без `HARNESS_LLM_TIMEOUT` до остановки новых юнитов. Отказ оставляет ответы, что уже есть. Прочие задачи не меняются: промпты побайтно прежние, фаза 1 прежняя. Цена: прозаическая задача стоит около вдвое больше единиц (prose2 ~8–9K против ~4–5K), невыполнимая прозаическая с `IMPOSSIBLE` от FAST — ещё вызов ALT.
- **Второе мнение на первый `IMPOSSIBLE`** (раунд 19, `llm_routes.second_opinion`, `HARNESS_SECOND_IMPOSSIBLE`). В 2b для search и data без прозаической базы, если программа FAST напечатала `IMPOSSIBLE` или кончилась «kb page or field not found» без запасного ответа, `MODEL_ALT` один раз получает тот же промпт; его программа исполняется как программа маршрута. Ответ берётся, только если прогон чистый, значение нужной формы и это не `IMPOSSIBLE`, не заглушка, не `None`, не страница целиком, не отказ другими словами (impossible, cannot, not enough, insufficient, undetermined, no such / data / information / answer) и не печать готового литерала. Он идёт запасным ответом и заполняет только пустое место: ранее записанный запасной ответ не заменяет, задача остаётся `unparsed`, и финальный REASON-проход может взять её, как раньше. Модельно-независимый вердикт невыполнимости до 2b не доходит и не пересматривается. Условия: потрачено меньше половины бюджета, новые юниты не остановлены, вызов помещается в учёт. Math, проза и coding не затронуты. Повод: far8 search_8002 («Who is older, A or B?»), где FAST сразу печатал `IMPOSSIBLE` в одном прогоне из шести.
- **Повторный проход** для юнитов, у которых вызов не получил ответа от прокси. Math-задача, где REASON уже дал вердикт, а FAST оказался недоступен, в этом проходе получает только программу FAST; если недоступен был REASON, его спрашивают снова.
- **Финальный REASON-проход.** Если бюджета потрачено меньше половины, для не более чем 10 нерешённых math/data/search задач с наградой не ниже медианы (по всем задачам, лучшие первыми) делается по одному вызову `MODEL_REASON` с просьбой написать программу (3000 токенов). Голый ответ без программы (одна строка нужной формы, например `108`) принимается как есть, `IMPOSSIBLE` так не принимается. У search-вопроса о числе или да/нет формы нет: голое число принимается, голое «Yes» — нет (нужна программа). Math-задачи, которые REASON уже решил в 2b, сюда повторно не берутся. Для search с `kb/` этот проход получает тот же готовый словарь `kb`, и те же правила: не найдено или placeholder, а также напечатанная страница — `unparsed` без догадки. Потолок в 10 вызовов не зависит от учёта: прокси может не вернуть usage.
- **Подтверждение 2a** (`HARNESS_CONFIRM_2A`, по умолчанию включено; `harness/confirm.py`), после 2b, повторного прохода и финального прохода `MODEL_REASON`, перед 2d. Для data ответ 2a проверяет независимая программа `MODEL_FAST`, которая не видит ни спецификацию, ни ответ 2a; при расхождении голосует программа `MODEL_ALT`. Ответ 2a меняется, только если оба голоса согласны между собой и каждый напечатал ровно одну строку в той же форме, что ответ (целое для `exact_int`, простое число, короткое имя), сравнение с точностью не ниже показанной в ответе 2a. Группы идут по убыванию награды; новые голоса не покупаются после половины бюджета. Два нулевых голоса не заменяют ненулевой числовой ответ 2a. Math и search по умолчанию не подтверждаются. В math спецификация 2a задаёт правило округления явно, а программы обеих моделей округляли одинаково неверно и в прогоне Docker заменили верный ответ (82920 на 82908); исправлений в math не было ни разу. Голос search стоил около 1400 единиц на задачу и ни разу не изменил ответ. С `HARNESS_CONFIRM_MATH=1` (раунд 10, `confirm.confirm_reason`) ответ 2a в math проверяет `MODEL_REASON`, не видя ответа 2a; при расхождении голосует программа `MODEL_FAST`, затем программа `MODEL_ALT`. Ответ 2a меняется, только если все три голоса согласны, причём ALT не должен был уйти на те же веса, что уже голосовали (REASON и FAST — одно семейство, их согласие может быть одним и тем же прочтением текста). Голоса math идут после всех голосов data. Цена на llm8 около 12 тыс. единиц, а единственное изменение ответа было неверным (`math_0076`, ещё до голоса ALT), поэтому по умолчанию выключено.
- **2d.** Независимая проверка зелёных одиночных coding-фиксов (`HARNESS_VERIFY_CODING`, `harness/arbitrate.py: verify_fix`), последним этапом: открытые задачи важнее второго мнения по уже отвеченной. `MODEL_FAST` (400 токенов) пишет свой фикс по багованной функции и видимым тестам, не видя нашего; ответ, упёршийся в лимит, не считается. Совпало поведение на probe-входах — фикс подтверждён одним вызовом. Иначе зелёный кандидат идёт в арбитраж 2c (все различающиеся probe-строки показываются первыми), и фикс меняется только при согласии обеих моделей. Частичные ремонты, ambiguous и infeasible задачи не проверяются. Ремонт, после которого каждая изменённая функция по AST совпала с известным текстом функций из примеров организаторов (`reverse_words`, `total`, `maximum`, `average`, `first_n`, `count_even`) или с окончательным выученным текстом (раунд 11), окончателен сразу, без 2c и 2d (в note `repaired by mutation, canonical`); с раунда 10 известный текст подставляется и до перебора, при совпадении формы (см. фазу 1, coding), и тогда подсказка 2d для остальных функций показывает настоящий исходный текст. В траектории единица `verify:<task_id>`, в её note голоса моделей. Замер раунда 7: 0 сломанных из 221 верного фикса; 2 исправления на отложенном наборе, 0 на наборах без неверных зелёных фиксов.
- **Аудит соперничающих форм** (раунд 14, `harness/audit.py`, `HARNESS_AUDIT_FORMS`). Ловит «тихую» ошибку, которую видимый assert не ловит, в функциях не из примеров: одна и та же функция в разных задачах набора стоит зелёной в разных формах, и модели выбирают верную.
  - Где стоит: последним этапом фазы 2, после 2d и повторного прохода; если фаза 1 ничего не оставила, фаза 2 запускается только ради него (без 2a/2b).
  - Условия запуска: в наборе ≥ 3 coding-задач и ≥ 3 решённых с `answer.txt` на диске; до остановки новых юнитов ≥ 60 с; потрачено меньше 50 % бюджета. Порог 50 % проверяется ещё и перед каждым юнитом аудита.
  - Перепись: не дольше `min(60 с, 10 % остатка)`, до 10 с на прогон тестового файла; держатель — решённая задача, у которой зелёные все `test_*.py`; workspace с одинаковыми по AST `mylib.py` и тестами (ключ включает имена тестовых файлов) голосуют один раз, но замену получают все. Неполная перепись не даёт ничего.
  - Кандидаты: функция верхнего уровня без декораторов, определённая один раз, самодостаточная, имя не из шести примеров организаторов. Соперники: разные по AST формы с одинаковыми параметрами и в сумме ≥ 2 голоса под видимым тестом.
  - Пробы: не больше 6 самых частых форм на ≤ 60 входах (видимые вызовы набора, их варианты, краевые значения), подпроцесс через `run_python`. Формы с одинаковым поведением показываются одним вариантом, а голоса варианта — голоса только его самой частой формы; файлы с равносильной формой не трогаются.
  - Показ: до 3 вариантов и до 6 различающих строк; непротестированные формы показываются, только если протестированный вариант один. `MODEL_FAST` и `MODEL_ALT` отвечают номером (8 токенов), ALT видит варианты и столбцы в обратном порядке.
  - Решение: замена только при согласии FAST и ALT. Вариант с меньшим числом голосов, чем у первого, требует ещё `MODEL_REASON` (1500 токенов, порядок по голосам, ответ читается только с последней непустой строки: «k», «Option k», «Answer: k», «Final answer: k»; иначе замены нет), не больше 6 таких вызовов за прогон. Ничья решается согласием двух моделей.
  - Запись: переписываются только файлы показанных проигравших вариантов, функция подставляется в `mylib.py` целиком, и только если все тестовые файлы держателя остаются зелёными (20 с на файл, во временной копии); запись атомарная, после остановки новых юнитов новые файлы не берутся. `answer.txt` не меняется. Не больше 20 функций за прогон, самые частые первыми.
  - В траектории юнит `audit:<имя функции>` (см. «Траектории»).
  - Замер (коммит 78c3ebc, BUDGET=100000, без Docker; расход — только аудит): trap1 (`scripts7/mk_trap.py`) 65 → 83/90 за 430 единиц; v4 coding 15 → 19/20 за 174 (из них +2 — шум живого 2b, сам аудит дал `gcd`, `median`, `last_n`); maj (тихая ошибка в большинстве файлов) 7 → 45/94 за 1391; pool 25/25, 0 вызовов; примеры организаторов 0 единиц (coding-задач меньше трёх). Неверных замен 0: все заменённые функции проходят скрытые тесты. Ранняя версия (d745f7a), которая переписывала и непоказанные непротестированные формы и давала ALT тот же порядок, что FAST, получала 90/90, 17/20 и 63/94; потери после правки — цена правил «непоказанное не переписывается» и «ALT видит обратный порядок» (часть прежних согласий была выбором по позиции).
- **Ревью решённых coding-файлов** (раунд 18, `harness/review.py`, `HARNESS_REVIEW_CODING`). Фаза 1 и лестница останавливаются на первом зелёном прогоне, а скрытые тесты жюри вызывают те же функции на других входах. Тихая ошибка, до которой не дотянулся ни один видимый assert, остаётся в файле. Аудит ловит её только там, где одна функция стоит в наборе в разных формах; ревью читает каждый файл сам по себе.
  - Где стоит: после аудита, последним этапом фазы 2; `answer.txt` не меняется. Ревью стартует, если до остановки новых юнитов ≥ 60 с и потрачено меньше 50 % бюджета; порог 50 % проверяется и перед каждым юнитом. Юнит без 60 с до остановки не делает вызов: он не успел бы проверить ответ.
  - Какие файлы: решённые, с `answer.txt`, зелёные на всех видимых `test_*.py` и `*_test.py`, не длиннее 9000 символов, и хотя бы одна функция в них не известный текст. Известные — шесть функций примеров организаторов и финальные выученные тексты набора (`final` у `_mine_texts`); нефинальный выученный текст может быть самой общей ошибкой набора и ревью проходит. На шаблонных наборах (v5, примеры) — 0 вызовов.
  - Вызовы: `MODEL_FAST` читает файл и тесты и возвращает исправленные функции в формате `FUNC` или `NONE` (700 токенов, ответ, упёршийся в лимит, отбрасывается). `MODEL_ALT` спрашивается тем же промптом, только если FAST что-то переписал.
  - Замена функции — только когда всё сразу: её переписали обе модели (или одна из них и `MODEL_REASON`, см. ниже); не известный текст. На пробных входах (видимый вызов и значения тех же форм, у непротестированной функции — общие формы по числу параметров) обе версии ведут себя одинаково везде, где наша функция возвращает значение, и хотя бы на одном таком входе отличаются от неё. Видимые тесты со вставленной версией зелёные, все тестовые файлы.
  - Сломанная версия отклоняется целиком: NameError, ImportError, UnboundLocalError, тайм-аут, падение, рекурсия, любое исключение не из области значений (ValueError, KeyError, IndexError, ZeroDivisionError), TypeError и AttributeError там, где наша функция возвращает значение. Блок `FUNC`, где рядом с функцией стоят импорт или вспомогательная функция (`apply_patch` их отбросил бы), не принимается. Значения, обрезанные по пределу repr пробы, ни согласия, ни различия не показывают.
  - Исключения: сохраняется версия, которая нигде не бросает там, где наша возвращает значение (иначе она отбросила бы нашу защиту от пустого входа). Если бросают обе, версия сохраняется только тогда, когда обе бросают одно и то же исключение из области значений на каждом таком входе, его имя есть в docstring или комментариях функции или в видимых тестах для неё («ValueError if their lengths differ»), и в тексте версии стоит `raise <Имя>`. Тесты называют исключение для функции строкой, где имя функции стоит целым словом (`mean` — не `mean_abs`), вызовом `assertRaises(X, f, …)` и блоком `with pytest.raises(X):` / `with self.assertRaises(X):`, если последняя инструкция блока — вызов этой функции без других вызовов в аргументах (`mean(parse("1,x"))` называет исключение `parse`, а не `mean`; раунд 19, `HARNESS_REVIEW_NAMED`).
  - Запись атомарная, файл перечитывается перед записью; пробы и прогоны не стартуют после остановки новых юнитов. Любое сомнение оставляет файл. В траектории юнит `review:<task_id>`.
  - Третье мнение (раунд 19, `HARNESS_REVIEW_REASON`). `MODEL_REASON` спрашивается один раз на файл, если две версии расходятся (одна сломана, а другая нет; разные значения там, где наша функция возвращает значение; одна бросает, другая возвращает) или функцию переписала только одна модель, а её версия одна прошла бы все правила (отличие от нашей, ничего не сломано, правило исключений, видимые тесты зелёные). Промпт тот же, с одной строкой «Look only at <имена>: rewrite it if it is wrong, else reply NONE.»; чужих ответов он не видит (вопрос обо всём файле стоил на far8 coding_8004 3057 единиц и пустой ответ). 2000 токенов, `reasoning_effort=low`. Версия REASON и версия FAST (затем ALT) проходят те же правила, что пара FAST и ALT; в траектории «sided [...] with FAST/ALT». Предел на прогон: 6 вызовов или 8000 единиц; файл только с односторонними случаями не берёт последние 2 вызова и 2000 единиц, их оставляют расхождениям. Ворота те же: 60 с до остановки, меньше 50 % бюджета. Согласованные замены записываются до вызова REASON. Замер: trap1 coding_7024 (`sum_squares`) — 85 → 90/90.
  - Недетерминированные функции не судятся: наша версия пробуется дважды, и если на каком-то входе она отличается от себя (random, время), функция остаётся как есть и REASON не спрашивается. Каждая версия пробуется отдельным подпроцессом, даже при одинаковом тексте.
  - Методы классов (раунд 19, `HARNESS_REVIEW_METHODS`). Сценарии строятся из видимых тестов, которые создают класс и вызывают метод (до 8 тестов, `setUp` первым; тесты с фикстурами и parametrize пропускаются, у dunder-методов кроме `__init__` сценариев нет): тело теста исполняется, литеральные входы меняются на значения тех же типов (по одному, затем парами, до 400 сценариев), ожидаемые значения assert не меняются. Сравниваются значения, на которые смотрят assert, результаты вызовов и состояние объектов: публичные атрибуты, а для согласия двух версий ещё и атрибуты с одним подчёркиванием (отличие от нашей версии читается только по публичным). Версия вставляется внутрь класса; версия, меняющая декораторы метода, не принимается. Модуль под тестом грузится по имени, под которым его импортируют тесты (`mylib`, `pkg.core`, `wallet.ledger`); модуль пакета с относительным импортом или импортом другого модуля `workspace` не ревьюется (ни одна проба его не загрузит). Метод, который ни один видимый тест не вызывает, отбрасывается до вызова ALT.
  - Шире пробные входы (раунд 21, `HARNESS_REVIEW_PROBES`). Строковые варианты видимого аргумента: смена каждого знака (`+02:00` → `-02:00`), замена каждого числа на выведенные из него (n+1, n−1, 0, 10n+9, 2n, 10^ширина, −n), строка без пробелов; у них свой лимит, 40 на аргумент, после 400 основных входов, поэтому пары видимых аргументов не вытесняются. Аргументы `Decimal`, `Fraction`, `date`, `datetime`, `timedelta` из видимых вызовов: свой дочерний процесс, значения, выведенные из видимого (±0,005, −v, 10v, v/8; день до, семь дней после, конец месяца), и общие. Констант из скрытых тестов какого-либо набора нет. Вызовы без параметра по умолчанию подряд в одном процессе показывают изменяемое значение по умолчанию; если отличие есть только на них, а докстринг говорит о намеренно сохраняемом состоянии (unique, across calls, cache), это не улика. Зависание нашей версии — улика, только если повторный запуск её одной с таймером 5 с (не больше двух входов) снова упирается в таймер ревью; у дочернего процесса ревью свой таймер (`BaseException`, `<exc:ProbeAlarm>`), и `raise TimeoutError` самой функции зависанием не считается. Подмена исключения (наша пропускает `ZeroDivisionError`, обе версии бросают `ValueError`) — улика, только если в докстринге есть предложение, где это исключение названо выбрасываемым при нашем условии (zero для деления, empty/index для `IndexError`, key/missing для `KeyError`); упоминание в `except` не в счёт.
  - Остаточные риски: обе модели могут сойтись на другом прочтении функции или класса; REASON — та же модель, что FAST, с рассуждением, поэтому пара FAST + REASON — не два независимых мнения.

## Оценка расхода и отбор задач

`harness/estimator.py`: оценка вызова до его выполнения = длина контекста в символах / 3 (символов на токен) / 10 (вес prompt) + базовая константа маршрута: JSON-спецификация 80, программа 120, coding 400 (ответ модели). Для coding контекст — `mylib.py` + тесты + 2000 символов запаса.

Как оценка влияет на работу:
- юниты 2a и 2b упорядочиваются по `reward / оценка` (по убыванию); арбитраж 2c дёшев и идёт отдельным этапом до 2b;
- перед запуском юнит проверяется: если его оценка не помещается в остаток бюджета за вычетом резерва, он пропускается и берётся следующий, более дешёвый;
- перед каждым вызовом цена вызова резервируется под учёт: полный `max_tokens`, если помещается, иначе ограниченный остатком; вызов с лимитом меньше 100 токенов (1000 для рассуждений) не делается.

Точность оценки невелика: на шести юнитах «программа» из прогонов ниже фактический расход составил от 0,8 до 4,3 оценки (один из шести дороже в 4,3 раза). Для выбора порядка этого достаточно, для строгого прогноза нет.

## Бюджет и защита от обрыва

Организаторы (2026-11-09): прокси при исчерпании бюджета ничего не присылает, запуск просто останавливается, засчитывается то, что успело записаться. Поэтому харнесс не ждёт сигнала, а следит сам:
- свой счётчик `TokenLedger` (`harness/budget.py`) по usage ответа прокси; если usage нет, списывается оценка (prompt = длина сообщений / 4, completion = лимит вызова);
- 5 % бюджета не тратится вообще (резерв), оставшееся резервируется на вызовы в полёте (`hold`);
- вызов, завершившийся таймаутом или оборванным соединением, списывается фиксированной суммой (`TIMEOUT_CHARGE` 1500, не больше стоимости самого вызова), без добавки за вход; ответ 402/403 считается исчерпанием бюджета;
- (раунд 15) каждый неудачный запрос, дошедший до прокси, списывается по входу: организаторы 2026-11-09 сказали, что «любые запросы, которые ушли, это входные токены». Это 5xx, 429 (и повторённые, и последний), прочие 4xx, повтор 400 без structured output, повторы после исправления адреса или имени модели, 402/403, ошибки без HTTP-статуса, кроме обрыва и таймаута, и неудачный пинг другой модели. Вход оценивается с запасом: длина сообщений / 3, а не / 4, как у успешного ответа без usage, и не больше того, что вызов зарезервировал (`hold`), поэтому счётчик не выходит за бюджет. Бесплатны только отказ в соединении (запрос не ушёл) и зависший пинг (1 токен);
- каждый ответ и каждый запасной ответ пишутся на диск сразу, поэтому остановка в любой момент не теряет уже найденное;
- общий дедлайн 3300 с: после него новые юниты фазы 1 не стартуют, юниты фазы 2 прекращаются; за 150 с до дедлайна новые юниты фазы 2 не начинаются.

**Сбои прокси.** Состояние здоровья ведётся по каждой модели. Ошибка 5xx или соединения повторяется с паузами (`HARNESS_RETRY_DELAYS`, затем удвоение до 60 с); ответ 429 — по тем же паузам. Если сбоит одна модель, а другие отвечают, вызов уходит на другую; если не отвечает ни одна, харнесс ждёт, а не сдаётся, и объявляет прокси мёртвым только после `HARNESS_PROXY_DEAD_S` секунд (по умолчанию весь дедлайн) без единого успешного ответа. Ответ 400 на `response_format`/`extra_body` клиент один раз повторяет без них и дальше их не посылает.

С раунда 15 долгий сбой 5xx/429 тратит бюджет: каждая попытка списывается по входу своего промпта, а в каждом цикле пауз пробуют около трёх воркеров. Двухминутный сбой обходится примерно в 2–5 тыс. единиц при промптах в 1–3 тыс. токенов, часовой — в десятки тысяч. Поэтому высокий `spent` после сбоя ожидаем, а не ошибка. Такой расход может раньше закрыть пороги в 50 % бюджета (финальный REASON-проход, аудит). Так требуют правила организаторов: ушедший запрос стоит входных токенов.

## Невыполнимые задачи

Задача невыполнима, если ответа нет при имеющихся данных (человека или компании нет в базе, деление на 0, нет колонки или файла, запрошена величина вне данных). Такой задаче `answer.txt` не создаётся: так сказано в FAQ организаторов от 7 ноября («не создавайте файл»; за пропуск баллов нет). Исключение (раунд 15): если задачу признала невыполнимой фаза 2, а запасной ответ уже записан, он остаётся на диске. Организаторы 11 ноября: файл для невыполнимой задачи «можете создавать, можете не создавать, мы его не будем учитывать… ни штрафов, ни бонусов».

Кто и когда признаёт задачу невыполнимой:
- Фаза 1 (0 токенов): по результату исполнения спецификации. Примеры: data-запрос про скидку, налог, прибыль и подобное при отсутствии такой колонки; неизвестная начальная сущность в search; деление на ноль в math.
- math (раунд 11, `math_solver.missing_quantity`): количество названо без числа. Слова: `several`, `some`, `a few`, `few`, `many`, `multiple`, `various`, `numerous`, `a number of`, `a handful of`, `a lot of`, `lots of`, `an unknown (unspecified, undisclosed, certain …) number (amount, quantity) of`, буквы `N`, `x`, `k` (не перед `percent`). Правило срабатывает, только если каждое предложение задачи разбирается грамматикой решателя, а предложение с таким словом разбирается после подстановки числа. Предложение, которое разбирается и так, не трогается, поэтому `some` как обычное слово ничего не включает. Кроме того, предложение `start` ровно одно и стоит первым, вопрос один и стоит последним. Исключения: `a couple of`, `a pair of`, `a dozen` (это числа) и предложение, где другой множитель равен 0 (недостающее число ничего не меняет). Нота «quantity not given: …».
- data (раунд 11, `data_solver`):
  - фильтр product или region со значением, которого нет в файле и которого нет среди восьми слов из примеров организаторов (`widget`, `gadget`, `gizmo`, `sprocket`, `north`, `south`, `east`, `west`), даёт `infeasible` («the product/region does not occur in the file»). Если в файле есть то же значение в единственном или множественном числе, итог `unparsed`. Слово организаторов, которого нет в маленьком файле, даёт честный 0;
  - регионы для этого правила собираются со всех строк файла. Поэтому `max_units`/`min_units` по комбинации product и region, которой нет в файле, теперь `unparsed` (уходит в фазу 2), а не `infeasible`;
  - месяц вне 1..12 при полностью разобранном вопросе даёт `infeasible` («month outside 1..12»), если в колонке `month` файла нет значений вне 1..12 (месяцы нескольких лет). Иначе, а также при свободном разборе, итог `unparsed`.
  - (раунд 14, `data_solver._ABSENT`, `_nowhere`, `_bare_template`) величина, которой нет ни в одной колонке, при любом агрегате. Вопрос целиком: «what is/was the» + `total`/`average`/`mean`/`overall`/`combined`/`maximum`/`minimum`/`highest`/`lowest`/`largest`/`smallest` + `discount`/`tax`/`shipping`/`profit`/`margin`/`commission`/`rebate`/`refund`/`tip` (и мн. ч.) + необязательно `given`/`charged`/`paid`/`applied`/`collected`/`amount`/`rate` + необязательный фильтр (`on|in|from|by|across|per|of|for` и слово, например «given on product 'gadget'», «of region 'west'»). Правило срабатывает, только если выполнены все условия: все колонки файла из `_UNDERIVING` (order_id, region, product, month, units, price, quantity, date, customer, category и подобные; `unit_price` в список не входит, поэтому пара `price` + `unit_price` никогда не доказывается); в рабочем каталоге нет ничего, кроме названного CSV (costs.csv или promos.csv могли бы дать величину под другим именем); сырая инструкция — это предложение о файле, вопрос и только шаблонные предложения организаторов дословно («Use bash with python3 to compute it.», «Work only inside the current directory.», «When you are done, write ONLY the final answer to the file answer.txt …»), а слово встречается в ней ровно один раз; CSV слово нигде не называет, ни в каком регистре и форме (`Discounts`, `discount_pct`). Нота «the file has no X column». Для вопроса «total …» правило стало строже раунда 13: тогда оно не проверяло ни каталог, ни шаблон.
- coding: строгое доказательство противоречия видимых тестов (`coding_solver.provable_contradiction`), в двух видах, и с раунда 11 ещё два правила фазы 1 (последние два пункта). Файл тестов в обоих видах противоречия строгой формы: импортируются только `unittest` и `mylib`, в классах `unittest.TestCase` только тестовые методы (без `setUp`), рефлексия вроде `skipTest` запрещена, учитываются только утверждения верхнего уровня метода; чистота вызываемых функций проверяется.
  - Один и тот же вызов чистой функции с литеральными аргументами должен давать два разных ожидаемых значения в прямых `assertEqual`.
  - (раунд 10) Одно простое утверждение одного из восьми видов (`assertEqual`, `assertNotEqual`, `assertTrue`, `assertFalse`, `assertGreater`, `assertGreaterEqual`, `assertLess`, `assertLessEqual`), аргументы которого — простые литералы или вызовы чистых функций `mylib`, закреплённые где-либо в файле прямым `assertEqual` за простым значением (не dict и не set), ложно при этих значениях. Например, `assertGreater(m.total([1, 2, 3]), 10)` рядом с `assertEqual(m.total([1, 2, 3]), 6)`, или `assertEqual(1, 2)`. Само утверждение (а для вызовов — закрепляющий их тест) должно быть красным на текущем `mylib.py`; утверждение только из литералов должно быть красным само.
  - (раунд 11, `coding_solver.known_text_fails`) Красный тест, использующий только функции в окончательном известном тексте: тексте из примеров организаторов или окончательном выученном (см. «Фаза 1»). Тесты написаны под этот текст, поэтому тест, красный на нём, не пройдёт ни при каком `mylib.py`. Известный текст либо стоит в файле как есть, либо подставлен вместо слипа в одну правку (`_one_edit`: одна пара отличий от известного текста, вызывается только то, что вызывает известный текст). Во втором случае тест судится, только если функция красная сама по себе на текущих красных тестах (её тест использует только её и известные тексты, стоящие как есть). Тест, где есть выученный текст, судится, только если других функций в нём нет: тест `f(g(x))` с двумя выученными текстами mining не проверял. Тест только на текстах примеров судится всегда. Функция определена один раз, без декораторов, не читает других имён модуля. Форма файла строгая, как у `provable_contradiction`, а `mylib.py` состоит только из определений и ничего не перепривязывает во время работы (`global`, `exec`, `setattr` …). Нота «a test fails on the known correct text». Тест раунда 10 `test_known_text_changed_again_by_the_search_shows_the_real_original` переписан: теперь его задача `infeasible`, и сценарий «перебор снова меняет подставленный известный текст» простым файлом не достигается.
  - (раунд 11) Файл тестов не разбирается (`ast.parse` байтов файла, поэтому BOM и строка кодировки допустимы; ловится только `SyntaxError`, включая `TabError` и нулевые байты). Нота «the test file does not parse». По очкам это равно раунду 10: тогда такая задача доходила до лестницы, но прогон тестов давал `<unknown>`, и `DONE` был невозможен. Правило экономит около 400 единиц лестницы. Ошибка импорта, сломанный `mylib.py` и BOM невыполнимостью не считаются.

  - (раунд 14) Ещё два вида противоречия, оба в той же строгой форме файла: `self.assertTrue(c)` и `self.assertFalse(c)` одного вызова `c` чистой функции с литеральными аргументами где угодно в файле (истинность ничего не закрепляет, с `assertEqual` не сравнивается); `self.fail()` или `self.fail(<константа>)` прямо в теле теста (не внутри `if`/`try`/`with`/`for`, не в помощнике, без декоратора и `skipTest`): второй проход читает его как `assertTrue(False)`, и доказательство засчитывается, только если этот тест красный сейчас. Проверка — там же, где у прежних видов: в фазе 1 после перебора или по времени и в `fix_coding` до вызова модели, 0 единиц. Правило «тесты импортируют несуществующий модуль» выключено (`MISSING_IMPORT_PROOF = False`, см. «Переменные окружения»).

  Замеры раунда 11: `scripts3/coding_infeasible.py` — 10 из 17 `infeasible` (8 по известному тексту, 2 по противоречию), `scripts3/coding_matrix.py` — 53 из 55.

  Замеры раунда 14 (бесплатные доказательства): проход правил по `runs/` и наборам экспертов 2–7 (5942 coding- и 5015 data-задач) против dfd1430 — 73 изменённых вердикта (56 data, 17 противоречий coding; с включённым правилом модуля было 87), все на невыполнимых по построению, на выполнимых 0; `tools.fuzz` 0 WRONG (seed 1000 и 2000, по 1200 задач); наборы по генераторам других команд (`scripts7/mk_ext.py`, вживую): koz7 254/254, единицы 4594 → 283, re11 241/241, 2189 → 319 (замерено до выключения правила модуля: в koz7 одна такая задача, около 670 единиц); примеры организаторов 0 единиц.

В фазе 1 доказательство проверяется, когда перебор не нашёл ремонта или кончилось время (0 единиц). В фазе 2 оно проверяется до вызова модели, с красными тестами текущего `mylib.py`, поэтому оба вида работают и там (задача, у которой фаза 1 была убита жёстким таймаутом 100 с до собственной остановки). Правила раунда 11 работают только в фазе 1: разбор файла тестов проверяется до перебора, известный текст — до подстановок и при подстановке вместо слипа.

**Принятые остаточные риски раунда 11.**
- «3 против 0»: одинаковый баг, который не пойман ни в одной задаче, повторён минимум в трёх задачах. Он выучивается как окончательный текст и даёт неверный `canonical` без 2c и 2d или ложный `infeasible`.
- Посылка правила для текстов из примеров: текст организаторов верен во всех задачах. Задача, где правильна функция с защитой, которую известный текст убирает (замена дала ровно текст примера), получит `infeasible`.
- Одно имя с одной формой и разным смыслом в разных задачах. От этого защищает только перекрёстная проверка, и только в задачах, которые mining успел прогнать.
- Mining недетерминирован при обрыве по времени: какие задачи успели проголосовать, зависит от их порядка и скорости машины. Обрыв делает все тексты слабыми, но не отменяет их.
- «months 12 through 13» даёт `infeasible`, хотя декабрь посчитать можно.
- Неразбираемый файл тестов = `infeasible`. Если скрытый файл цел, а сломан только видимый, награда потеряна. По очкам это то же, что в раунде 10: ответа не было и тогда.
- Разбор зависит от версии Python (в Docker 3.11.11): синтаксис новее 3.11 в видимых тестах даёт `infeasible`. Это тоже равно раунду 10: такие тесты не запускались и тогда.

**Принятые остаточные риски раунда 14.**
- Голоса аудита не независимы: все три модели из семейства Qwen, а FAST и REASON на одной базе `qwen3.8-27b`. «Все три выбрали вариант меньшинства» — более слабое доказательство, чем звучит.
- Позиционное смещение: ALT видит обратный порядок, и при двух вариантах смещение к первому месту разводит голоса. При трёх вариантах средний стоит вторым у обеих моделей, и смещение к середине коррелирует. REASON видит порядок по голосам, поэтому меньшинство у него никогда не первое; это работает против подтверждения, то есть консервативно.
- Непоказанные непротестированные формы никогда не переписываются, поэтому неверная форма без теста остаётся неверной (на trap1 это 7 баллов).
- Аудит может перевернуть окончательный выученный текст раунда 11 и фикс, подтверждённый 2d: окончательный текст A стоит в части файлов, а в файлах, где функция не под тестом, осталась исходная форма B. Если FAST и ALT выбирают A, она попадает и туда, где её никто не проверял; если все три модели выбирают B, B заменяет A во всех A-файлах. Так задумано (аудит ловит ошибку большинства, для этого нужны три голоса).
- Формы, совпавшие на ≤ 60 пробах, считаются одним вариантом; ничья 1:1 решается согласием FAST и ALT без REASON (та же сила, что в 2c).
- Медленная, но верная форма на пробах выглядит зависшей: все входы идут одним подпроцессом с общим лимитом 5 с, после таймаута все следующие входы тоже `<exc:Timeout>`, и неверная быстрая форма может победить. На замеренных наборах не встречалось.
- Аудит тратит токены там, где раунд 13 тратил 0: фаза 2 запускается ради него, если фаза 1 решила всё, а в наборе есть соперничающие формы. Цена на замерах 0–1391 единиц; худший случай — 20 функций по два вызова плюс 6 вызовов REASON с лимитом вывода 1500. При равенстве баллов решают токены, но баллы важнее.
- Бесплатные доказательства coding (противоречие, `self.fail`, `assertTrue`/`assertFalse`) исходят из того, что противоречие видимого файла есть и в скрытом, хотя скрытый файл заменяет видимый. Это та же ставка, что у прежнего противоречия `assertEqual`; от окружения она, в отличие от правила модуля, не зависит.
- Правило отсутствующей колонки: определение величины в любом месте инструкции (рядом с вопросом, в шаблонной фразе, в хвосте после «When you are done») правило выключает, потому что вокруг вопроса допускается только дословный шаблон. Остаётся посылка, что величину нельзя вывести из units и price: если жюри считает, например, прибыль равной выручке, награда потеряна. В шаблоне и наборах организаторов такого нет.

Известное ограничение: часть невыполнимых задач получает ответ (в прогонах ниже 1 из 20 и 3 из 18), если разбор приводит их к осмысленному значению, например пустое среднее даёт `0`. Это осознанное приведение: по регламенту неверно решённая задача не засчитывается; 11 ноября организаторы подтвердили, что штрафа за ответ на невыполнимую задачу нет. Поэтому ложный `infeasible` выполнимой задачи гораздо дороже ответа невыполнимой: бесплатные доказательства срабатывают только при полной уверенности.

## Траектории

Файл `trajectory.jsonl` в `HARNESS_LOG_DIR`: события всех задач в порядке выполнения, пишет `harness/scheduler.py`, каждая запись сбрасывается на диск сразу. Файл дописывается, а не перезаписывается: при повторном запуске с тем же каталогом прогоны смешиваются. В Docker по команде жюри каталог лежит в `tmpfs` и исчезает с контейнером; чтобы забрать траекторию, задайте `HARNESS_LOG_DIR` в примонтированный каталог (см. выше).

Поля записи: `phase` (1 или 2), `task_id`, `status`, `cost`, `elapsed` (с), `note`; у фазы 2 ещё `unit`, `model`, `calls`. `cost` — сумма стоимости собственных вызовов юнита (у фазы 1 — 0). `unit`: `group:<тип>:<число задач>`, `batch:<тип>:<число групп>`, `arbitrate:<task_id>`, `reason:<task_id>`, `verify:<task_id>` (2d), `audit:<имя функции>` (аудит раунда 14) или `<task_id>` для 2b. У строки аудита `task_id` равен `audit:<имя>`, статус `unit`, а note — итог голосования и список заменённых файлов: «both models chose option 1 of votes [3, 2]; 4 forms; replaced in ['coding_7003']», «all three models chose minority option 2 of votes [4, 3]; …», «no agreement ([1, 2]) on [4, 3]; …», «minority … not confirmed by …», «forms do not differ on the sample calls; …». `calls` — список `{model, prompt_tokens, completion_tokens, cost}`, у неудавшихся вызовов ещё `error`. Стоимость группы записывается на её первого участника. Служебные статусы: `unit` (вызовы юнита без закрепившейся задачи), `deadline`, `budget_exhausted`, `error`, `unattributed` (расхождение с учётом бюджета, чтобы сумма `cost` по файлу равнялась расходу). Пример записи:

```json
{"phase": 2, "task_id": "data_analysis_0074", "status": "solved", "unit": "data_analysis_0074", "model": "qwen3.8-27b-noreason", "cost": 112.0, "calls": [{"model": "qwen3.8-27b-noreason", "prompt_tokens": 280, "completion_tokens": 84, "cost": 112.0}], "elapsed": 1.371, "note": "model program"}
```

Приложены траектории (`docs/trajectories/`):
- `2026-11-09-d0008e4-live4.jsonl` и `2026-11-09-d0008e4-llm3.jsonl` — два прогона ниже (коммит d0008e4);
- `2026-11-08-train.jsonl` и `2026-11-08-live-r2.jsonl` — прогоны раундов 1 и 2 на более ранних версиях кода; в первом поле `run` отличает прогоны.

## Безопасность

Изоляцию обеспечивает контейнер: корень только для чтения, без capabilities, закрытая сеть с выходом только на прокси организаторов, лимиты памяти и PID.

Единственная сетевая цель харнесса — `LLM_BASE_URL`; ключ берётся из `LLM_API_KEY`, нигде не записывается и не передаётся подпроцессам (`harness/proc.py`: `LLM_API_KEY`, `LLM_BASE_URL`, `BUDGET` убираются из окружения). Код задачи и программы модели запускаются только через `run_python`. Других адресов в коде образа нет, при запуске ничего не скачивается. Жюри не запускает контейнер, который пытается выйти в интернет, поэтому в образе выставлены `HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE`, `HF_DATASETS_OFFLINE`, `HF_HUB_DISABLE_TELEMETRY`, `OTEL_SDK_DISABLED`, `OTEL_*_EXPORTER=none`, `DO_NOT_TRACK`: библиотеки, которые тянет openjiuwen, не пробуют скачивание или экспорт. Замер: образ с перехватом сетевых вызовов Python (`sys.addaudithook`) на 13 задачах, в том числе через модель, обращался только к `LLM_BASE_URL`.

Локальных нейросетевых моделей нет. `transformers` и ещё несколько пакетов приходят транзитивно из `openjiuwen`; харнесс их не импортирует.

Код задачи и программы модели выполняются отдельным процессом на временной копии каталога задачи, с лимитами на posix: память `RLIMIT_AS` 2 ГиБ, время CPU `RLIMIT_CPU` (таймаут × 4 + 5 с), размер файла `RLIMIT_FSIZE` 1 ГиБ, вывод обрезается до 8 КБ, один поток BLAS/OpenMP. Это защита от ошибок программ, а не граница безопасности: сетевой и файловой изоляции у процесса нет, она остаётся за контейнером. Подпроцессы аудита раунда 14 (прогоны тестов и пробы форм) идут тем же путём, через `run_python` во временных копиях, без `LLM_API_KEY`, `LLM_BASE_URL` и `BUDGET`; в прокси уходят только тексты функций и результаты проб, как в 2c.

`kill`, `killpg` и чтение `/proc` используются только для завершения собственных зависших потомков по таймауту. Контейнер работает от root (без capabilities), потому что владелец смонтированного `/data/tasks` заранее неизвестен.

Охват формулировок организаторов неизвестен: нераспознанное уходит в 2a/2b. `MODEL_FAST` выбран замером на нераспознанных math-задачах фазы 2a (`gen_tasks --novel 1.0 --seed 31`: 12 из 12 против 2 из 12 у `MODEL_ALT`); на data/search и coding выборка мала или замера нет.
