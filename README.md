# SysCall harness (openJiuwen Challenge 2026)

Харнесс решает задачи четырёх типов (math, data_analysis, search, coding) с минимальным расходом токенов. Большую часть задач он решает детерминированно, без обращений к LLM; модель вызывается только для того, что не удалось разобрать правилами.

## Сборка и запуск

Команда жюри (из регламента):

```bash
mkdir -p "$OUT" && chmod 777 "$OUT"

docker build -t "hack:latest" . && \
timeout -k 1000s 1h docker run --rm --name "run-${TEAM}" \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  "hack:latest" \
  /app/run_agent.py --tasks-dir /data/tasks
```

- Образ: `python:3.11.11-slim-bookworm`, зависимости закреплены в `requirements.txt` (`openjiuwen==0.1.19` и транзитивные версии, собрано под linux x86_64). Ничего не скачивается при запуске, ключей в образе и репозитории нет.
- Переменные окружения: `LLM_BASE_URL`, `LLM_API_KEY` (выдаёт жюри), `BUDGET` — бюджет токенов (по умолчанию 100000), необязательная `HARNESS_LOG_DIR` — каталог траекторий (по умолчанию `<tempdir>/harness`, то есть `/tmp/harness`). `TASKS` — запасной каталог задач, `OUT` — необязательный файл решений (см. ниже).
- Ручки времени (все необязательны, читаются в момент использования; пустое, нечисловое, отрицательное или бесконечное значение откатывается к умолчанию с одним предупреждением в лог): `HARNESS_LLM_TIMEOUT` — таймаут вызова модели, с (180); `HARNESS_RETRY_DELAYS` — задержки повтора на 429 через запятую, с (`2,4,8,16,30`); `HARNESS_DEADLINE_S` — общий дедлайн прогона, с (3300); `HARNESS_STOP_NEW_BEFORE_DEADLINE_S` — за сколько секунд до дедлайна новые юниты фазы 2 не стартуют (150); `HARNESS_PHASE1_TIMEOUT_CODING` и `HARNESS_PHASE1_TIMEOUT_DEFAULT` — таймаут фазы 1 на coding-задачу и на остальные, с (100 и 15). `HARNESS_LLM_CONCURRENCY` — число одновременных вызовов модели (3), читается при старте; нецелое или меньше 1 значение молча заменяется умолчанием.
- Каталог задач: первый из `--tasks-dir`, позиционного аргумента (если это каталог), env `TASKS`, `/data/tasks`, в котором есть `task.json` (иначе первый существующий каталог); выбранный источник и отвергнутые кандидаты пишутся в stderr. Файл решений: `--out`/`--output` или env `OUT`; это JSON `{task_id: answer}`, переписывается атомарно после каждого ответа (если путь — существующий каталог или оканчивается на `/`, пишется `answers.json` внутри). Ошибка записи файла не мешает `answer.txt` и не роняет запуск.
- Если прокси отвечает 400 на `response_format`/`extra_body`, `LLMClient` один раз повторяет запрос без них и дальше их не отправляет (`structured_ok`); такой откат не считается отказом прокси и не списывает `TIMEOUT_CHARGE`.
- Результат: `answer.txt` в каталоге каждой задачи (`/data/tasks/<task>/answer.txt`). Код выхода всегда 0.
- Запись `answer.txt`: временный файл рядом + `fsync` + `os.replace`; если каталог не позволяет создавать файлы, запись идёт напрямую в `answer.txt`. Каждый ответ пишется сразу после решения, а не в конце. В `/app` ничего не пишется (файловая система только для чтения, рабочие данные уходят в `/tmp`).
- Каталог задач должен быть доступен на запись для root внутри контейнера: при `--cap-drop ALL` каталог другого владельца с правами 755 блокирует запись каждого `answer.txt` (обходного пути внутри контейнера нет).
- Если `LLM_BASE_URL`/`LLM_API_KEY` не заданы, работает только фаза 1.

## Архитектура

### Фаза 1: детерминированные решатели (0 токенов)

`harness/solvers/*`, 8 процессов (`spawn`, таймаут на задачу: 15 с, для coding 100 с; собственный лимит coding-решателя на 15 с меньше таймаута coding (85 с при 100; при таймауте ≤ 30 с — половина), чтобы решатель успел остановиться сам и сохранить предварительный ответ и подсказку арбитража до того, как процесс убьют; лимиты CPU/памяти на процесс (`proc.make_limits`) действуют на подпроцессы тестов и программ, а не на сами рабочие процессы):

- math: разбор предложения по грамматике шаблонов и вычисление; шаги вроде «loses a quarter» выражаются шагами-выражениями (`x-x//4`). Отрицательный запас ответом не считается (см. «Запасные ответы»);
- data_analysis: разбор запроса в спецификацию запроса к CSV и выполнение. Метрики: `sum_units`, `sum_revenue`, `count_orders`, `avg_price`, `avg_units`; `top_product_*` и `top_region_*` по units/revenue/orders (ответ — название победителя); `max_units`/`min_units` (наибольшее и наименьшее число единиц в одном заказе); округление «rounded to N decimal places» (`decimals`, только для `sum_revenue` и `avg_*`; хвостовые нули сохраняются, кроме проверки `exact_int`);
- search: разбор цепочки запросов к базе знаний (kb chain spec). Если у человека спрашивают поле компании (Founded/Headquarters), поиск идёт через его работодателя (`Employer`);
- границы месяца в data (loose): «through/up to/until/till month N» = 1..N, «from month N onwards» и «months N onwards» = N..12; одиночная граница «from/by month N» (и «after/before») даёт `unparsed`; если рядом упомянуты и `units`, и `revenue` (вне определения «units multiplied by price»), это две меры и вопрос уходит в `unparsed`. Названия месяцев («in July») и порядковые («in the 7th month») читаются как один месяц; если слово совпадает со значением продукта/региона, `unparsed`. «Where does X work?» остаётся `unparsed` (непонятно, компания или город);
- search нормализует типографские апострофы и тире (’ ‘ ʼ – — → ' -) и неразрывные пробелы при поиске имён и в формулировках;
- «свободные» разборщики (`parse_loose` в data и search) работают по закрытому словарю: берут вопрос, только если в нём ровно одно имя из базы знаний или значения из колонок CSV, а любой неизвестный квалификатор («excluding», «first 3 months», «fewest», «per unit») даёт `unparsed`, а не угаданный ответ (fail closed);
- coding: ремонт кода инверсными однотокенными мутациями; кандидаты проверяются на видимых тестах только во временных копиях каталога задачи; найденное исправление записывается атомарно в настоящий `workspace/mylib.py` (то же делает `fix_coding` в фазе 2). Детерминированный выбор пишется на диск сразу. Затем решатель проверяет неоднозначность: для каждой исправленной функции перебирает альтернативные однотокенные исправления, проходящие весь видимый прогон, и группирует их по поведению на входах из видимого вызова. Если групп больше одной, решатель выбирает между ними по правилу ничьей (`coding_solver._edit_rank`): разворот сравнения (`<` ↔ `>`) лучше смены строгости (`>` → `>=`), а она лучше отрицания (`>` → `<=`, `==` → `!=`); `+` ↔ `-` и `/` ↔ `//` лучше прочих замен операторов; константа, сдвинутая к нулю, лучше сдвинутой от нуля; исправление, убирающее пустую операцию (`x % 1`, `x // 1`, `x * 1`, `--x`), выигрывает, а создающее её проигрывает. При равенстве действует порядок мутантов (сначала константы). Если лучше ранжирована не та группа, что нашёл ремонт, она записывается на диск после полного зелёного прогона. Лучшая группа идёт в арбитраж первым вариантом. Задача получает предварительный ответ `DONE` и помечается неоднозначной (арбитраж 2c). Если исправлена только часть тестов, лучший частичный `mylib.py` записывается вместе с предварительным `DONE`. Перебор ограничен временем решателя и никогда не стоит ответа.

**Предварительные ответы.** Ответ, записанный как предварительный (partial repair или неоднозначный выбор), остаётся в `answer.txt`, а задача идёт в фазу 2 за улучшением. Неудачная поздняя попытка ответ не отзывает, успешная его заменяет.

**Запасные ответы (best guess).** Три решателя возвращают `unparsed` вместе с запасным ответом, если решить надёжно нельзя: math если после списания запас уходит ниже нуля (само значение); data при ничьей за первое место (первый в порядке строк CSV); search при расхождении чтений вопроса (первое чтение). Так же поступают 2a и 2b, если ответ и после повтора не прошёл проверку формы (последнее значение неверной формы). Запасной ответ пишет только финальный проход планировщика и только если у задачи нет `answer.txt`; вердикт фазы 2 `infeasible` его отзывает.

### Фаза 2: LLM (через `Model.invoke` из openJiuwen)

Для задач, которые не разобрала фаза 1.
- 2a. Нераспознанные math/data/search задачи группируются по шаблону (`harness/templates.py`). Модель один раз на группу выдаёт JSON-спецификацию, которую исполняют те же исполнители, что и в фазе 1 (`harness/json_route.py`). Обычно один вызов покрывает всю группу; всего на группу не больше 4 вызовов (повтор невалидного JSON и повтор по форме ответа, у каждого не больше одного повтора JSON). Для math спецификация — `{"start": N, "steps": ["x-{N2}*{N3}", "x-x//4"]}`: шаги-выражения над `x` вычисляет безопасный AST-вычислитель (`math_solver.execute_steps`: только `x`, целые, `+ - * //`, унарный минус, скобки; `//0` — infeasible, |значение| > 10^18 — unparsed); старый формат `ops` тоже принимается. Модель просят отвечать JSON в одну строку. Схема data перечисляет все метрики исполнителя, включая `top_*`, `max_units`, `min_units` и необязательное `decimals`; `{"impossible": true}` разрешён только для величин, которых нет ни в одной метрике (скидка, налог, прибыль, несуществующая колонка).
  - search: модель отвечает `{"entity": "{E1}", "hops": ["Mentor", "Employer", "Headquarters"]}` — список полей по порядку от начальной сущности, последнее звено — запрошенное поле; перед исполнителем это превращается в `{"entity", "path": hops[:-1], "field": hops[-1]}`. Допустимы только пять полей (Born, Employer, Mentor, Founded, Headquarters, без учёта регистра); пустой список или чужое имя — невалидная спецификация (один повтор с причиной, как при битом JSON). Старый ответ вида `path`/`field` тоже принимается. В шаблонах search слотом становятся и имена с дефисом (`Nikolai-Felix Lindqvist`) и средним инициалом (`Quinn D. Muller`); для math и data шаблонизатор прежний.
  - search: вопрос, идущий по связи в обратную сторону (`mentee`, `mentored by X`, `does X mentor`, `X mentors`, `is X mentoring`, `works for/at C`, `employed by C`, `employees`), в 2a не задаётся: группа сразу получает `unparsed` («reverse relation») без вызова и уходит в 2b, который может перебрать всю базу. Промпт дополнительно просит отвечать на такие вопросы `{"impossible": true}`.
  - Проверка формы ответа (`harness/shape.py`, без модели): по формулировке вопроса search ожидается год из 4 цифр (Born/Founded) или имя, а не число (Headquarters/Employer/Mentor); для math и data с проверкой `exact_int` — целое. Участникам группы с ответом не той формы делается один повтор на `MODEL_ALT` с подсказкой (прежний ответ и ожидаемая форма); если и он не той формы, задача `unparsed` с запасным ответом и идёт в 2b. Участники с верной формой свои ответы сохраняют; если на повторе кончился бюджет, их ответы всё равно записываются.

- 2c. Арбитраж неоднозначных coding-задач (`harness/arbitrate.py`). Два независимых вызова на задачу, одновременно: `MODEL_FAST` и `MODEL_ALT` (`ARBITRATE_MODELS`). В промпте до 4 функций, варианты показаны как изменения строк относительно сломанной функции плюс таблица результатов вариантов на примерах вызова. Ответ модели — только номера вариантов, `max_tokens` 8. Выбор функции меняется, только если обе модели назвали один и тот же вариант, отличный от детерминированного; при расхождении, мусорном ответе или недоступности одной модели остаётся детерминированный выбор (обе недоступны — `unparsed`); при поддержке прокси включается `guided_regex`, при ответе 400 клиент повторяет запрос без него, мусорный ответ — один повтор без регулярки. Выбор, отличный от детерминированного, записывается в `mylib.py` только после полностью зелёного видимого прогона (сначала все замены, затем каждая по отдельности); тесты не меняются. Порядок фазы 2: 2a, затем 2c, затем 2b; арбитрированная задача в 2b не возвращается, неудачный арбитраж оставляет детерминированный выбор. Модели арбитража — `ARBITRATE_MODELS` (см. «Выбор модели»).

- 2b. Запасной путь для остальных: синтез программы моделью (`harness/llm_routes.py::solve_with_program`), программа исполняется в песочнице. До двух программ на `MODEL_FAST` (вторая — с ошибкой первой); если программа напечатала ответ не той формы (та же проверка `harness/shape.py`), делается ровно один дополнительный вызов на `MODEL_ALT` с подсказкой, то есть не больше 3 вызовов на задачу; ответ, так и не прошедший проверку, становится запасным. Для coding: лестница патчей `fix_coding` — `MODEL_FAST` (qwen3.8-27b-noreason), затем `MODEL_ALT` (qwen3.6-35b-a3b-noreason), затем `MODEL_REASON` (qwen3.8-27b) с низким reasoning (последний шаг, до 3000 токенов, выполняется, если награда задачи ≥ 3 или в бюджете осталось больше 50 %). Если попытка уменьшила число падающих тестов, следующая стартует от её частичного результата.

### Выбор модели

Имена моделей лежат в `harness/config.py` (`MODEL_FAST`, `MODEL_ALT`, `MODEL_REASON`, `ARBITRATE_MODELS`). `MODEL_FAST` выбран замером на нераспознанных фазой 1 задачах из `gen_tasks --novel 1.0 --seed 31` (по 15 math/data/search, потолок 30 вызовов на модель): на math qwen3.8-27b-noreason решила 12 из 12 достигнутых задач с ответом, qwen3.6-35b-a3b-noreason только 2 из 12; расход по счётчику бюджета 2575 против 3691 токена. Измерялся только math и только фаза 2a: лимит вызовов закончился внутри 2a, до 2b дело не дошло. На data/search выборка слишком мала для вывода; coding (`fix_coding`) и 2b (`solve_with_program`) на qwen3.8-27b-noreason не измерялись.

`ARBITRATE_MODELS` (арбитраж 2c) = (`MODEL_FAST`, `MODEL_ALT`): арбитраж единственный маршрут, который заменяет уже работающий детерминированный ответ, поэтому смена выбора требует согласия двух моделей. Замер раунда 3 (задача 22) на трёх наборах: 100 трудных coding (`gen_tasks --seed 74 --difficulty hard`), 146 пар «функция × видимый случай» из `tools.gen_tasks.LIB` и отложенный набор 150 трудных coding (`--seed 75`, при подборе правила ничьей не смотрелся). Было (фаза 1 без правила ничьей, одна модель): 92/100, 144/146, 147/150, сломано 3, 2 и 3 верных выбора. Стало (правило ничьей и согласие двух моделей): 95/100, 146/146, 149/150, сломано 0 на всех трёх. Одна фаза 1 без модели: 86 → 94 из 100, 135 → 145 из 146, 130 → 144 из 150. Цена: два вызова вместо одного, около 87 единиц на задачу против 43.

Задачи в фазе 2 упорядочиваются по отношению «награда / оценка стоимости» (`harness/estimator.py`): сначала самые выгодные.

Оценка стоимости до вызова (`harness/estimator.py`): длина контекста в символах делится на 3 (символов на токен), промпт взвешивается с коэффициентом 1/10, как в учёте бюджета, и добавляется базовая константа маршрута (JSON-спецификация 80, программа 120, coding 400 токенов на ответ модели). Для coding контекст — `mylib.py` + тесты + 2000 символов запаса; для программы — инструкция + описание workspace. Константы подобраны по тренировочным прогонам (см. «Результаты»).

## Расход токенов

`harness/budget.py`, `TokenLedger`: учёт идёт по ответу прокси. Списываются completion-токены + prompt/10. Для вызова, закончившегося таймаутом, ответом 5xx или оборванным соединением, фиксированно списывается 1500 токенов (`TIMEOUT_CHARGE`). 1% бюджета держится в резерве. Уже записанные ответы остаются на диске независимо от бюджета. Параллельность LLM-вызовов — 3 по умолчанию (потолок аккаунта у dev-провайдера; финальный прокси допускает до 5, меняется переменной `HARNESS_LLM_CONCURRENCY`), таймаут вызова 180 с. Общий дедлайн 3300 с, новые юниты не стартуют за 150 с до него.

## Невыполнимые задачи

Если ответа не существует (человека или компании нет в базе, деление на 0 при разбиении, отсутствует файл или колонка, запрошена величина, которой нет в данных), задача считается невыполнимой: `answer.txt` не создаётся. Если задачу признала невыполнимой фаза 1, токены на неё не тратятся; если это сделала модельная программа с `IMPOSSIBLE`, токены на вызов модели уже потрачены. Такой вывод делает фаза 1 по результату исполнения спецификации, либо программа, написанная моделью в пути 2b, если она напечатала последней строкой `IMPOSSIBLE` (в промпте модели это разрешено, когда ответа по данным нет).

Кто и когда признаёт задачу невыполнимой:
- Фаза 1: по результату исполнения спецификации (0 токенов). Новые вердикты: в data запрос «total discount/tax/shipping/profit/margin/commission/rebate/refund/tip», если такой колонки нет в CSV (`cost` сюда не входит: его можно понять как units×price, поэтому он идёт в 2a/2b); неизвестный продукт или регион при запросе наибольшего/наименьшего заказа. Среднее по пустой выборке отвечается `0`. Начальная сущность search с «грязным» именем (притяжательный `'s`, служебные слова) не даёт `infeasible`, а становится `unparsed` и идёт в 2a/2b.
- coding: противоречивые видимые тесты (один вызов с двумя разными ожидаемыми значениями, `coding_solver.contradictory_tests`); проверяется только после неудачного ремонта, 0 токенов.
- 2a (JSON-спецификация модели): окончательно принимается только `solved`. `infeasible` из 2a окончательный лишь для вердиктов, не зависящих от разбора моделью: деление на ноль и отсутствие начальной сущности в базе знаний (только если эта сущность — значение слота, дословно стоящее в инструкции; имя, которое модель исказила или написала сама, даёт `unparsed`). Любой другой `infeasible` (выдуманное поле, неверное имя файла, иная папка базы) считается `unparsed`, и задачу пробует путь 2b.
- 2b: программа модели с `IMPOSSIBLE`.

## Траектории

Один файл `trajectory.jsonl` в `HARNESS_LOG_DIR` (по умолчанию `/tmp/harness`): события всех задач в порядке выполнения, пишет планировщик `scheduler.py`, каждая запись сбрасывается на диск сразу.

Поля записи: `phase` (1 или 2), `task_id`, `status`, `cost`, `elapsed` (с), `note`; у записей фазы 2 ещё `unit`, `model`, `calls`.
- `cost` — сумма стоимостей собственных вызовов модели этой единицы работы (completion + prompt/10, таймаут — `TIMEOUT_CHARGE`), а не разница счётчика бюджета: параллельные вызовы других единиц в неё не попадают. У фазы 1 `cost` 0.
- `unit` — имя единицы фазы 2: `group:<тип>:<число задач>` для группы 2a, `arbitrate:<task_id>` для 2c, `<task_id>` для 2b. `model` — модель последнего вызова. `calls` — список вызовов `{model, prompt_tokens, completion_tokens, cost}`, у вызова, за который списан `TIMEOUT_CHARGE` (таймаут, 5xx, оборванное соединение), ещё `error` с текстом ошибки.
- Стоимость группы 2a целиком записывается на её первого закреплённого участника (`cost` и `calls`), у остальных участников группы `cost` 0.
- Статусы задач: `solved`, `infeasible`, `unparsed`. Служебные статусы фазы 2 (`task_id` = имя единицы): `unit` — вызовы единицы, ни одна задача которой не закрепилась (например, группа 2a, целиком ушедшая в 2b); `deadline`, `budget_exhausted`, `error` — единица прервана. В конце прогона, если сумма `cost` по файлу не совпадает со счётчиком бюджета, пишется запись `status: "unattributed"` с `task_id: null` и разницей в `cost`, так что сумма `cost` по траектории равна расходу прогона.

## Результаты

Тренировочные наборы создаёт `tools.gen_tasks` (100 задач, `--infeasible 0.2 --novel 0.2`; во втором раунде генератор v2 с большим числом формулировок). Прогон: Docker по команде жюри, `BUDGET=100000`, реальная модель. Сводные траектории раунда 1: `docs/trajectories/2026-11-08-train.jsonl` (поле `run` отличает прогоны). Генератор делает часть формулировок «вне грамматик» и 20 % невыполнимых задач, поэтому цифры фазы 1 на нём измеряют подгонку под наш генератор, а не точность на задачах организаторов; защита от этого — fail-closed разбор.

| Прогон | score / max | math | data | search | coding | токены | время |
|---|---|---|---|---|---|---|---|
| раунд 1, seed 7, до настройки | 198 / 211 | 20/20 | 18/19 | 21/22 | 17/19 | 8448 | 93 с |
| раунд 1, seed 8, до настройки | 220 / 240 | 18/21 | 17/19 | 20/20 | 19/20 | 8264 | 106 с |
| раунд 1, seed 8, после настройки | 228 / 240 | 18/21 | 19/19 | 20/20 | 19/20 | 1445 | 25 с |
| раунд 2, живой Docker, seed 61, n=100 | 239 / 239 | все | все | все | все | 114 | 37 с |

Ячейки по типам: верно / выполнимых задач типа. Невыполнимые задачи в score не входят: `answer.txt` для них не создаётся. Остальные получили ответ по принятому правилу (неизвестный продукт даёт 0), штрафа за них нет.

Раунд 2, стенд фазы 1 (без модели, `tools.gen_tasks` v2, seed 51, n=800): 97,5 % выполнимых задач решено верно; math, data и search 100 %, coding 90,3 %. Остаток coding — неоднозначные исправления и сложные мутации, которые закрывают 2c и 2b.

Раунд 2, живой Docker (100 задач, seed 61, команда жюри, реальная модель), траектория `docs/trajectories/2026-11-08-live-r2.jsonl`, 105 записей:
- фаза 1: 82 решено, 16 `infeasible`, 2 `unparsed` (coding без `mylib.py`; в фазе 2 они снова `unparsed`); 3 coding-задачи помечены неоднозначными;
- фаза 2: 3 арбитража 2c, все с примечанием «arbitration kept the choice» (изменённых выборов 0), 27–45 единиц на вызов, 114 токенов на весь прогон; единиц 2b на `MODEL_REASON` 0; статусов `deadline` и `error` 0; самая долгая единица 29 с.

Что изменила настройка раунда 1:
- Потолок аккаунта у провайдера: 3 одновременных запроса на все ключи, при 5 приходил 429 и вызов проваливался после 14 с ожидания. `LLM_CONCURRENCY` 5 → 3, задержки повтора 429 теперь 2, 4, 8, 16, 30 с.
- Программа модели для data_analysis/search получала в задании «запиши ответ в answer.txt» и писала файл вместо `print`; промпт теперь запрещает писать файлы (задача стоила 1096 токенов и не решалась, теперь 120).
- Противоречивые видимые тесты (один и тот же вызов с двумя разными ожидаемыми значениями) определяются без модели как `infeasible`: раньше модель подделывала результат (объект с `__eq__`, счётчик вызовов) и тратила 6300 из 8448 токенов seed 7.
- `CODING_BASE` оценки стоимости 200 → 400 (наблюдалось 165–2731 токенов на coding-задачу фазы 2; доказательная база слабая, на порядок ROI при бюджете 100000 не влияет).

Известные остатки (раунд 2 закрыл неоднозначные coding-исправления арбитражем, а формулировки вида «one quarter … moved» шагами-выражениями):
- грамматики покрывают формулировки нашего генератора; охват формулировок организаторов неизвестен, нераспознанное уходит в 2a/2b;
- осознанные приведения дают ответ на, вероятно, невыполнимую задачу (поле компании человека через работодателя, пустое среднее = `0`), штрафа за это нет;
- `fix_coding` и `solve_with_program` открываются на `MODEL_FAST` (qwen3.8-27b-noreason), эффект по токенам не измерен; лестница пробует и `MODEL_ALT`.
