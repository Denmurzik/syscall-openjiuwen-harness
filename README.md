# SysCall harness (openJiuwen Challenge 2026)

Харнесс решает задачи четырёх типов (math, data_analysis, search, coding) и для каждой выполнимой пишет `answer.txt`. Большую часть задач он решает детерминированно, без обращений к LLM; модель вызывается только для того, что не удалось разобрать правилами. Вызовы модели идут через `openjiuwen==0.1.19` (`Model.invoke`, провайдер OpenAI-совместимый, `harness/llm.py`); решатели, планировщик и учёт токенов написаны командой.

## Словарь

- **Фаза 1** — решатели без модели (0 токенов). **Фаза 2** — всё, что фаза 1 не решила, с вызовами модели: **2a** (JSON-спецификация на группу однотипных задач), **2c** (арбитраж coding), **2b** (программа или патч от модели на отдельную задачу). Порядок: 2a, 2c, 2b, повторный проход, финальный REASON-проход.
- **Юнит** — одна единица работы фазы 2 (группа 2a, батч 2a, арбитраж 2c или задача 2b); планировщик упорядочивает и запускает юниты.
- **Статусы задачи**: `solved` (ответ записан), `infeasible` (ответа не существует, `answer.txt` не создаётся), `unparsed` (решить не удалось; ответа нет, либо только запасной).
- **Запасной ответ (best guess)** — лучшее предположение, которое решатель отдаёт вместе с `unparsed`, когда надёжно решить нельзя. Он пишется на диск сразу и заменяется, если позже найдётся настоящий ответ.
- **Модели** (`harness/config.py`): `MODEL_FAST` = qwen3.8-27b-noreason, `MODEL_ALT` = qwen3.6-35b-a3b-noreason, `MODEL_REASON` = qwen3.8-27b (с `reasoning_effort=low`).
- **Расход** — completion-токены + prompt/10 (рассуждения входят в completion).

## Формат задач

Каталог задач содержит каталоги вида `<task_id>/` (примеры организаторов лежат в `tests/fixtures/examples/`):
- `task.json`: `task_id`, `task_type`, `instruction`, `reward` (баллы за задачу), `check` (`exact_int`, `exact_str` или `unittest`). В примерах есть ещё `expected`; по FAQ от 7 ноября в финальном наборе его уберут; харнесс его не читает.
- `workspace/` (если есть): для data_analysis `sales.csv`; для search папка `kb/` с markdown-файлами о людях и компаниях (поля Born, Employer, Mentor, Founded, Headquarters); для coding `mylib.py` и `test_mylib.py`. У math рабочего каталога нет.
- Ответ — файл `answer.txt` рядом с `task.json`; для coding это слово `DONE`, а исправление записывается в `workspace/mylib.py`.

Харнесс пропускает каталоги `__MACOSX` и начинающиеся с точки, допускает вложенность `каталог/каталог/<задачи>`, читает `task.json` с BOM; без числового `reward` берёт 1.0.

## Сборка и запуск

Команда жюри (из регламента; в регламенте у `docker build` нет контекста, здесь добавлена точка):

```bash
mkdir -p "$OUT" && chmod 777 "$OUT"

docker build -t "hack:latest" . && \
timeout -k 1000s 1h docker run --rm --name "run-${TEAM}" \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  "hack:latest" \
  /app/run_agent.py --tasks-dir /data/tasks
```

`TEAM` — имя команды, `TASKS` — каталог с задачами на хосте, `OUT` — каталог на хосте (по ответам организаторов 2026-11-09 `OUT` устарел: считается `answer.txt`), `hack-net` — сеть, которую создаёт жюри. `docker build` выполняется из корня репозитория. В контейнер попадают только `LLM_BASE_URL`, `LLM_API_KEY` и `TASKS` как каталог `/data/tasks`; `BUDGET` и `OUT` не передаются, поэтому в прогоне жюри действует бюджет по умолчанию 100000 (по FAQ организаторов от 7 ноября: «ориентируйтесь на бюджет 100K», «BUDGET=100000»; в регламенте числа нет; если настоящий бюджет меньше, харнесс этого не узнает, и прокси перестанет отвечать раньше, чем его счётчик исчерпается — см. «Бюджет и защита от обрыва»), а результат — только `answer.txt` в каталоге каждой задачи, у которой есть ответ (требование регламента «создать answer.txt в каталоге каждой задачи» относится к ним; для невыполнимой задачи FAQ от 7 ноября говорит: «не создавайте файл»). Код выхода всегда 0, в том числе при пустом каталоге задач: тогда харнесс молча находит ноль задач.

**Локальный запуск без Docker и без ключа** (Python 3.11+; работает только фаза 1):

```bash
pip install -r requirements.txt -r requirements-dev.txt
python -m tools.gen_tasks --out /tmp/set --n 100 --seed 1    # /tmp/set/tasks и /tmp/set/hidden
HARNESS_LOG_DIR=/tmp/set/log python run_agent.py --tasks-dir /tmp/set/tasks
python -m tools.evaluate --run /tmp/set --log /tmp/set/log/trajectory.jsonl
```

**Локальный запуск в Docker с настоящим прокси** (сверху вниз; нужны Python 3.11+ и Docker). Адрес и ключ прокси выдают организаторы; их кладут в окружение хоста и никогда не коммитят:

```bash
pip install -r requirements.txt                       # нужен для gen_tasks
python -m tools.gen_tasks --out set --n 100 --seed 1  # сначала набор: создаёт set/tasks и set/hidden
export LLM_BASE_URL=<адрес прокси>  LLM_API_KEY=<ключ>
docker network create hack-net
docker build -t hack:latest .
docker run --rm --network hack-net -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET=100000   -e HARNESS_LOG_DIR=/data/tasks/_harness_log   -v "$PWD/set/tasks:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp   --cap-drop ALL --security-opt no-new-privileges --cpus 8 --memory 16g --pids-limit 512   --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

Если смонтированный каталог пуст, харнесс молча выходит с кодом 0. Предупреждение «skipping task dir _harness_log» в stderr безвредно. `tests/chaos/fakeproxy.py` — подставной прокси для проверки без ключа (`python -m pytest -m chaos`).

Образ и сборка: `python:3.11.11-slim-bookworm`, зависимости закреплены в `requirements.txt` (`openjiuwen==0.1.19` и транзитивные версии, собрано под linux x86_64), при запуске ничего не скачивается. Локально собранный образ `hack:latest` весит 1,42 ГБ по `docker images` (лимит 4 ГБ), файлы репозитория занимают около 1 МБ (лимит 100 МБ).

Раскладка: `run_agent.py` (точка входа), `harness/` (`solvers/` — фаза 1; `json_route.py`, `arbitrate.py`, `llm_routes.py` — фаза 2; `llm.py` — клиент модели; `budget.py`, `estimator.py`, `scheduler.py`), `tools/` (генератор задач, оценщик, стенды), `tests/`, `docs/trajectories/`.

### Переменные окружения

- `LLM_BASE_URL`, `LLM_API_KEY` — прокси организаторов. Если не заданы, работает только фаза 1.
- `BUDGET` — бюджет токенов (умолчание 100000). `HARNESS_LOG_DIR` — каталог траекторий и логов (умолчание `<tempdir>/harness`, то есть `/tmp/harness`; на `tmpfs` с `--rm` он исчезает после прогона).
- `TASKS` — запасной каталог задач; `OUT` или `--out` — необязательный файл `{task_id: answer}`, который переписывается после каждого ответа. Он не нужен, считается `answer.txt`. Каталог задач берётся из `--tasks-dir`, позиционного аргумента, `TASKS`, `/data/tasks` (первый, где есть `task.json`); выбор пишется в stderr.
- Ручки времени и параллельности, все необязательны; пустое, нечисловое, отрицательное или бесконечное значение заменяется умолчанием с одним предупреждением (кроме `HARNESS_LLM_CONCURRENCY`: она заменяется молча): `HARNESS_LLM_TIMEOUT` — таймаут вызова модели, с (180); `HARNESS_DEADLINE_S` — общий дедлайн, с (3300; лимит жюри 3600); `HARNESS_STOP_NEW_BEFORE_DEADLINE_S` — за сколько секунд до дедлайна новые юниты не стартуют (150); `HARNESS_RETRY_DELAYS` — паузы повтора на 429 и при сбоях прокси, с, через запятую (`2,4,8,16,30`); `HARNESS_PROXY_DEAD_S` — сколько секунд без единого успешного ответа считать прокси мёртвым (по умолчанию равно дедлайну); `HARNESS_PHASE1_TIMEOUT_CODING` и `HARNESS_PHASE1_TIMEOUT_DEFAULT` — таймаут фазы 1 на coding-задачу и на остальные, с (100 и 15); `HARNESS_LLM_CONCURRENCY` — одновременных вызовов модели (3: потолок аккаунта у dev-провайдера, финальный прокси допускает до 5); `HARNESS_BATCH_2A` — батчинг групп в 2a (включён, `0`/`false` отключает). `HARNESS_CONFIRM_2A` — подтверждение ответов 2a для data голосованием независимых программ (по умолчанию включено, `0` отключает). `HARNESS_VERIFY_CODING` — независимая проверка зелёных одиночных coding-фиксов, этап 2d (включена, `0`/`false` отключает; около 60 единиц на проверенную задачу). `HARNESS_REASON_MATH` — math в 2b сначала решает `MODEL_REASON` (включено; `0` даёт ровно поведение раунда 9: ни REASON в 2b math, ни голосов по math). `HARNESS_CONFIRM_MATH` — подтверждение ответов 2a для math голосами REASON, FAST и ALT (по умолчанию выключено; работает только вместе с `HARNESS_REASON_MATH`).

### Запись ответов

Каждый ответ пишется сразу после решения: временный файл рядом, `fsync`, `os.replace`; если каталог не позволяет создавать файлы, пишется напрямую в `answer.txt`. В `/app` ничего не пишется. Каталог задач должен быть доступен на запись для root в контейнере (организаторы 2026-11-09 подтвердили, что будет); при недоступности в stderr печатается `TASKS DIR NOT WRITABLE: uid=… owner=… mode=…`. В конце на stdout выводится `solved=… infeasible=… unparsed=… spent=…`.

## Архитектура

### Фаза 1: решатели без модели

`harness/solvers/*`, 8 процессов (`spawn`), жёсткий таймаут на задачу: 15 с, для coding 100 с; coding-решатель останавливается сам за 15 с до этого (85 с), чтобы успеть записать предварительный ответ.
- **math**: разбор предложения по грамматике шаблонов и вычисление шагами-выражениями. Отрицательный запас ответом не считается (см. запасные ответы).
- **data_analysis**: разбор вопроса в запрос к CSV: суммы, количество заказов, выручка (в том числе с определением в скобках: «revenue (units * price)», «(units x price)», «(units times price)», «(units multiplied by price)» и обратный порядок «price … units»), средние, `top_product_*` и `top_region_*`, `max_units`/`min_units`, округление «rounded to N decimal places». Свободный разбор принимает только вопросы, где неизвестных слов нет; любой неизвестный квалификатор («excluding», «first 3 months», «per unit») даёт `unparsed`, а не угаданный ответ.
- **search**: разбор цепочки запросов к базе знаний (человек → работодатель → город штаб-квартиры и т. п.). Поле, не подходящее по виду сущности (Founded у человека), и обратные связи («кого наставляет X») не угадываются.
- **coding**: ремонт кода однотокенными мутациями; кандидаты проверяются на видимых тестах во временной копии каталога; найденное исправление записывается в настоящий `workspace/mylib.py`. Если подходящих исправлений несколько, решатель группирует их по поведению на видимых вызовах и выбирает по правилу ничьей (`coding_solver._edit_rank`: разворот сравнения лучше смены строгости, она лучше отрицания; константа, сдвинутая к нулю, лучше сдвинутой от нуля; исправление, убирающее пустую операцию вроде `x * 1`, лучше создающего её). Задача получает предварительный ответ `DONE` и идёт в арбитраж 2c. Перебор ограничен (400 мутантов, 9 вариантов на функцию) и касается только функций верхнего уровня.
  - **Известный текст до перебора** (раунд 10). Каждая функция, которую вызывает красный тест и чьё имя есть среди функций из примеров организаторов (`reverse_words`, `total`, `maximum`, `average`, `first_n`, `count_even`), по одной заменяется известным правильным текстом. Условия: функция верхнего уровня, без декораторов, с теми же параметрами; та же форма (`coding_solver._same_shape`: те же виды операторов, поэтому docstring, лишний `if` или ветка не проходят; вызываемые имена — подмножество имён известного текста и `sorted/max/min/len/sum/reversed`, поэтому `abs` или `round` не проходят; не больше защит-выражений, чем в известном тексте: `… if xs else None`, `x or 0`, `and` с операндом, не являющимся сравнением значений, вроде `xs and xs[0]` или `x is not None and …`); множество красных тестов строго уменьшается, и ни один зелёный не краснеет. Лишнее условие-сравнение (`x % 2 == 0 and x > 2`) защитой не считается и заменяется. Дальше перебор мутаций продолжается от результата. Если время кончилось, принятая замена остаётся частичным ремонтом. Результат, совпавший с известным текстом, окончателен сразу (`repaired by mutation, canonical`), без 2c и 2d; если перебор потом снова изменил заменённую функцию, подсказка 2d показывает настоящий исходный текст, а не известный. Принятые остаточные риски (та же форма, защита теряется при замене): `split(' ')` заменяется на `split()`; защита, записанная через `max`/`min` (`xs[:max(n, 0) + 1]`, `sum(xs) / max(len(xs) - 1, 1)`); второе условие `if` в генераторе списка. В тестах неоднозначности (`test_arbitrate.py`, `test_coding_solver.py`, `test_verify_coding.py`) функция переименована из `count_even` в `count_evens`, чтобы их фикстуры не попадали под известный текст. Замер: матрица из 55 правдоподобных багов (`scripts3/coding_matrix.py`, в 3 из них видимый тест уже зелёный) — 52/52 `canonical` (до раунда 10 29/52); live9 coding 17/17 при 0 единиц.

**Предварительные ответы.** Ответ, записанный как предварительный (частичный ремонт или неоднозначный выбор), остаётся в `answer.txt`, а задача идёт в фазу 2 за улучшением. Неудачная поздняя попытка его не отзывает.

**Запасные ответы.** Решатель возвращает `unparsed` вместе с запасным ответом, если решить надёжно нельзя: math при отрицательном запасе, data при ничьей за первое место, search при расхождении двух чтений вопроса. Так же поступают 2a и 2b, если ответ и после повтора не прошёл проверку формы (такая догадка `shape_mismatch` занимает только пустое место). Запасной ответ пишется на диск сразу, а не в конце: прогон могут остановить без предупреждения. Он заменяется настоящим ответом; вердикт `infeasible` фазы 2 его удаляет только если он не зависит от модели (`division by zero`, `start entity not found`); IMPOSSIBLE от модели запасной ответ оставляет (и задача остаётся кандидатом финального REASON-прохода): штрафа за неверный ответ нет, а модель называла выполнимые задачи невыполнимыми.

### Фаза 2: модель

Для задач, которые фаза 1 не решила (или решила предварительно).

- **2a.** Нераспознанные math/data/search задачи группируются по шаблону (`harness/templates.py`: числа и имена заменяются слотами). Модель один раз на группу выдаёт JSON-спецификацию (`harness/json_route.py`), её исполняют те же исполнители, что в фазе 1. Для math это `{"start": N, "steps": ["x-{N2}*{N3}", "x-x//4"]}` (шаги вычисляет безопасный AST-вычислитель: только `x`, целые, `+ - * //`); для search `{"entity": "{E1}", "hops": ["Mentor", "Employer", "Headquarters"]}`. Спецификация `{"impossible": true}` разрешена для величин, которых нет в данных; в math она возвращается на любой вопрос, кроме «сколько осталось в конце», и такая задача уходит в 2b. Проценты считаются как `x*N//100`. Расход на группу: обычно один вызов, плюс повтор при битом JSON и один повтор на `MODEL_ALT` при ответе не той формы (`harness/shape.py`: год из 4 цифр, имя, целое) или при числе шагов меньше числа операций в тексте. У search-вопроса, который спрашивает число или да/нет, формы нет и проверка не делается: вопрос начинается с «how many / how much / how old», «what is the (total) number of», «answer yes or no» или с глагола вопроса да/нет (`is/are/does/did/was/were/do/has/have/can/will`; «Can you tell me the year…» и «Do you know who…» вопросом да/нет не считаются и сохраняют форму года или имени, а «Can you tell me whether/if…» считается), либо такая фраза («how many», «number of», «yes or no») стоит в вопросе без явного who/which/where/when/«what city». «The largest (highest, most …) number of …» — выбор сущности, а не счёт: «Which company has the largest number of employees?» сохраняет форму имени. Вопросы, идущие по связи в обратную сторону, в 2a не задаются, а сразу уходят в 2b. Батчинг (группы упорядочены по номеру задачи): до 4 мелких групп одного типа (до 2 задач в каждой) получают спецификации одним вызовом; негодный элемент решается своим вызовом; так же один раз перезапрашивается своим вызовом участник батча, закончивший `unparsed` (кроме обратной связи, `impossible` и `shape_mismatch`). Сырая спецификация каждой группы пишется в лог `harness` на уровне INFO (до 300 символов).
- **2c.** Арбитраж неоднозначных coding-задач (`harness/arbitrate.py`): `MODEL_FAST` и `MODEL_ALT` независимо отвечают номером варианта (`max_tokens` 8). Выбор меняется только если обе назвали один и тот же вариант, отличный от детерминированного, и только после полностью зелёного видимого прогона; иначе остаётся детерминированный выбор. Замер раунда 3 на 100 трудных coding-задачах: 92/100 до, 95/100 после (одна модель, без правила ничьей и с ним вместе с согласием двух моделей); цена около 87 токенов на задачу против 43.
- **2b.** Запасной путь. Для math (раунд 10, `HARNESS_REASON_MATH`) сначала один вызов `MODEL_REASON` с просьбой написать программу (`reasoning_effort=low`, 3000 токенов), если выполнены все четыре условия: весь вызов помещается в учёт (оценка задачи + 3000); потрачено меньше 50 % бюджета; до момента, когда новые юниты перестают стартовать, осталось не меньше `HARNESS_LLM_TIMEOUT` + 60 с (иначе юнит отменили бы до программы FAST); задачу ещё не решил REASON (вердикт ставится только по ответу самой модели, не при недоступности или обрезке бюджетом). Ответ REASON нужной формы окончателен. `IMPOSSIBLE` от REASON принимается на веру: программа FAST после него не запускается (REASON 20 из 20 на выполнимых math; на v3 `math_9319` FAST записал ответ невыполнимой задаче), а уже лежащая на диске догадка остаётся (мягкий `infeasible`). Программа FAST запускается, только если REASON не дал вердикта или дал ответ не той формы; такой ответ сначала записывается как догадка `shape_mismatch`, ответ FAST его заменяет, догадка FAST — нет. Замер: llm8 math 28/28 за 3183 единицы (раунд 9: 3208), v3 math 13/14 за 3385. Худший случай: юниты 2b math упорядочены по оценке без учёта 3000 токенов REASON и поэтому идут раньше coding-лестниц и программ search/data. Если до 2b доходит 16 и больше math-задач (например, новые формулировки, от которых отказалась 2a), REASON стартует, пока не потрачено 50 % бюджета, а до трёх вызовов в полёте (около 3,1 тыс. каждый) добавляют ещё около 9 тыс., всего около 59 тыс. Каждый вызов длится до `HARNESS_LLM_TIMEOUT` (180 с) на трёх потоках. Финальный REASON-проход и голоса подтверждения data стоят за тем же порогом 50 % и тогда не получают ничего. Учёт при этом не превышается и дедлайн не срывается (проверка времени и резерв `hold` на каждый вызов); на замеренных наборах до этого далеко. Для math/data/search: программа от `MODEL_FAST` (до двух попыток, вторая с ошибкой первой, `max_tokens` 900: программы search, читающие базу знаний, на 400 обрезались), исполняется отдельным процессом на копии каталога (до 20 с); при ответе не той формы один вызов на `MODEL_ALT`. Для search с каталогом `kb/` база знаний уже загружена в словарь `kb` (заголовок страницы -> {поле: значение}): свой системный промпт, в user-тексте число страниц и по одному примеру страницы каждого вида, а загрузку файлов перед программой добавляет сам harness (программа модели исполняется под именем `<program>`). Нет страницы (`kb[...]`), либо программа напечатала `None`/`unknown`/`n/a`: итог `unparsed` («kb page or field not found») без повтора и без догадки. Страница есть, а спрошенного поля у неё нет (`KbFieldMissing`, раунд 10): один повтор, в котором перечислены существующие поля и подсказано, что обратную связь («кого наставляет X», «кто работает в X») ищут перебором `kb.items()` с `.get()`; повторный промах даёт прежний итог «not found». После повтора по полю догадка не сохраняется ни при каком исходе (модель недоступна, повтор формы исчерпан, конец попыток). В системном промпте правило: отвечать только спрошенным полем, а если у сущности такого поля нет, печатать `IMPOSSIBLE`; обратная связь и подсчёт отсутствующим полем не считаются. Напечатанные dict, list, tuple и представления словаря отвергаются (один повтор с просьбой напечатать одно значение) и никогда не становятся догадкой. Программа, печатающая голую константу (`print(340)`, число посчитано «в уме»), отвергается без запуска, один повтор с причиной. Если модель недоступна, берётся следующая (`chat_or_alt`). Для coding лестница патчей: `MODEL_FAST` (400 токенов), `MODEL_ALT` (600), `MODEL_REASON` (3000, выполняется при награде ≥ 3 или если осталось больше половины бюджета); следующая ступень стартует от частичного результата предыдущей.
- **Повторный проход** для юнитов, у которых вызов не получил ответа от прокси. Math-задача, где REASON уже дал вердикт, а FAST оказался недоступен, в этом проходе получает только программу FAST; если недоступен был REASON, его спрашивают снова.
- **Финальный REASON-проход.** Если бюджета потрачено меньше половины, для не более чем 10 нерешённых math/data/search задач с наградой не ниже медианы (по всем задачам, лучшие первыми) делается по одному вызову `MODEL_REASON` с просьбой написать программу (3000 токенов). Голый ответ без программы (одна строка нужной формы, например `108`) принимается как есть, `IMPOSSIBLE` так не принимается. У search-вопроса о числе или да/нет формы нет: голое число принимается, голое «Yes» — нет (нужна программа). Math-задачи, которые REASON уже решил в 2b, сюда повторно не берутся. Для search с `kb/` этот проход получает тот же готовый словарь `kb`, и те же правила: не найдено или placeholder, а также напечатанная страница — `unparsed` без догадки. Потолок в 10 вызовов не зависит от учёта: прокси может не вернуть usage.
- **Подтверждение 2a** (`HARNESS_CONFIRM_2A`, по умолчанию включено; `harness/confirm.py`), после 2b, повторного прохода и финального прохода `MODEL_REASON`, перед 2d. Для data ответ 2a проверяет независимая программа `MODEL_FAST`, которая не видит ни спецификацию, ни ответ 2a; при расхождении голосует программа `MODEL_ALT`. Ответ 2a меняется, только если оба голоса согласны между собой и каждый напечатал ровно одну строку в той же форме, что ответ (целое для `exact_int`, простое число, короткое имя), сравнение с точностью не ниже показанной в ответе 2a. Группы идут по убыванию награды; новые голоса не покупаются после половины бюджета. Два нулевых голоса не заменяют ненулевой числовой ответ 2a. Math и search по умолчанию не подтверждаются. В math спецификация 2a задаёт правило округления явно, а программы обеих моделей округляли одинаково неверно и в прогоне Docker заменили верный ответ (82920 на 82908); исправлений в math не было ни разу. Голос search стоил около 1400 единиц на задачу и ни разу не изменил ответ. С `HARNESS_CONFIRM_MATH=1` (раунд 10, `confirm.confirm_reason`) ответ 2a в math проверяет `MODEL_REASON`, не видя ответа 2a; при расхождении голосует программа `MODEL_FAST`, затем программа `MODEL_ALT`. Ответ 2a меняется, только если все три голоса согласны, причём ALT не должен был уйти на те же веса, что уже голосовали (REASON и FAST — одно семейство, их согласие может быть одним и тем же прочтением текста). Голоса math идут после всех голосов data. Цена на llm8 около 12 тыс. единиц, а единственное изменение ответа было неверным (`math_0076`, ещё до голоса ALT), поэтому по умолчанию выключено.
- **2d.** Независимая проверка зелёных одиночных coding-фиксов (`HARNESS_VERIFY_CODING`, `harness/arbitrate.py: verify_fix`), последним этапом: открытые задачи важнее второго мнения по уже отвеченной. `MODEL_FAST` (400 токенов) пишет свой фикс по багованной функции и видимым тестам, не видя нашего; ответ, упёршийся в лимит, не считается. Совпало поведение на probe-входах — фикс подтверждён одним вызовом. Иначе зелёный кандидат идёт в арбитраж 2c (все различающиеся probe-строки показываются первыми), и фикс меняется только при согласии обеих моделей. Частичные ремонты, ambiguous и infeasible задачи не проверяются. Ремонт, после которого каждая изменённая функция по AST совпала с известным текстом функций из примеров организаторов (`reverse_words`, `total`, `maximum`, `average`, `first_n`, `count_even`), окончателен сразу, без 2c и 2d (в note `repaired by mutation, canonical`); с раунда 10 известный текст подставляется и до перебора, при совпадении формы (см. фазу 1, coding), и тогда подсказка 2d для остальных функций показывает настоящий исходный текст. В траектории единица `verify:<task_id>`, в её note голоса моделей. Замер раунда 7: 0 сломанных из 221 верного фикса; 2 исправления на отложенном наборе, 0 на наборах без неверных зелёных фиксов.

## Оценка расхода и отбор задач

`harness/estimator.py`: оценка вызова до его выполнения = длина контекста в символах / 3 (символов на токен) / 10 (вес prompt) + базовая константа маршрута: JSON-спецификация 80, программа 120, coding 400 (ответ модели). Для coding контекст — `mylib.py` + тесты + 2000 символов запаса.

Как оценка влияет на работу:
- юниты 2a и 2b упорядочиваются по `reward / оценка` (по убыванию); арбитраж 2c дёшев и идёт отдельным этапом до 2b;
- перед запуском юнит проверяется: если его оценка не помещается в остаток бюджета за вычетом резерва, он пропускается и берётся следующий, более дешёвый;
- перед каждым вызовом цена вызова резервируется под учёт: полный `max_tokens`, если помещается, иначе ограниченный остатком; вызов с лимитом меньше 100 токенов (1000 для рассуждений) не делается.

Точность оценки невелика: на шести юнитах «программа» из прогонов ниже фактический расход составил от 0,8 до 4,3 оценки (один из шести дороже в 4,3 раза). Для выбора порядка этого достаточно, для строгого прогноза нет.

## Бюджет и защита от обрыва

Организаторы (2026-11-09): прокси при исчерпании бюджета ничего не присылает, запуск просто останавливается, засчитывается то, что успело записаться. Поэтому харнесс не ждёт сигнала, а следит сам:
- свой счётчик `TokenLedger` (`harness/budget.py`) по usage ответа прокси; если usage нет, списывается оценка (prompt = длина сообщений / 4, completion = лимит вызова);
- 5 % бюджета не тратится вообще (резерв), оставшееся резервируется на вызовы в полёте (`hold`);
- вызов, завершившийся таймаутом или оборванным соединением, списывается фиксированной суммой (`TIMEOUT_CHARGE` 1500, не больше стоимости самого вызова); ответ 402/403 считается исчерпанием бюджета;
- каждый ответ и каждый запасной ответ пишутся на диск сразу, поэтому остановка в любой момент не теряет уже найденное;
- общий дедлайн 3300 с: после него новые юниты фазы 1 не стартуют, юниты фазы 2 прекращаются; за 150 с до дедлайна новые юниты фазы 2 не начинаются.

**Сбои прокси.** Состояние здоровья ведётся по каждой модели. Ошибка 5xx или соединения повторяется с паузами (`HARNESS_RETRY_DELAYS`, затем удвоение до 60 с); ответ 429 — по тем же паузам. Если сбоит одна модель, а другие отвечают, вызов уходит на другую; если не отвечает ни одна, харнесс ждёт, а не сдаётся, и объявляет прокси мёртвым только после `HARNESS_PROXY_DEAD_S` секунд (по умолчанию весь дедлайн) без единого успешного ответа. Ответ 400 на `response_format`/`extra_body` клиент один раз повторяет без них и дальше их не посылает.

## Невыполнимые задачи

Задача невыполнима, если ответа нет при имеющихся данных (человека или компании нет в базе, деление на 0, нет колонки или файла, запрошена величина вне данных). Такой задаче `answer.txt` не создаётся: так сказано в FAQ организаторов от 7 ноября («не создавайте файл»; за пропуск баллов нет).

Кто и когда признаёт задачу невыполнимой:
- Фаза 1 (0 токенов): по результату исполнения спецификации. Примеры: data-запрос про скидку, налог, прибыль и подобное при отсутствии такой колонки; неизвестная начальная сущность в search; деление на ноль в math.
- coding: строгое доказательство противоречия видимых тестов (`coding_solver.provable_contradiction`), в двух видах. Файл тестов в обоих случаях строгой формы: импортируются только `unittest` и `mylib`, в классах `unittest.TestCase` только тестовые методы (без `setUp`), рефлексия вроде `skipTest` запрещена, учитываются только утверждения верхнего уровня метода; чистота вызываемых функций проверяется.
  - Один и тот же вызов чистой функции с литеральными аргументами должен давать два разных ожидаемых значения в прямых `assertEqual`.
  - (раунд 10) Одно простое утверждение одного из восьми видов (`assertEqual`, `assertNotEqual`, `assertTrue`, `assertFalse`, `assertGreater`, `assertGreaterEqual`, `assertLess`, `assertLessEqual`), аргументы которого — простые литералы или вызовы чистых функций `mylib`, закреплённые где-либо в файле прямым `assertEqual` за простым значением (не dict и не set), ложно при этих значениях. Например, `assertGreater(m.total([1, 2, 3]), 10)` рядом с `assertEqual(m.total([1, 2, 3]), 6)`, или `assertEqual(1, 2)`. Само утверждение (а для вызовов — закрепляющий их тест) должно быть красным на текущем `mylib.py`; утверждение только из литералов должно быть красным само.

  Решение принимается только по доказательству: при сомнении задача идёт дальше, потому что ложный `infeasible` стоит награды за задачу. В фазе 1 доказательство проверяется, когда перебор не нашёл ремонта или кончилось время (0 единиц). В фазе 2 оно проверяется до вызова модели, с красными тестами текущего `mylib.py`, поэтому оба вида работают и там (задача, у которой фаза 1 была убита жёстким таймаутом 100 с до собственной остановки).
- 2a: окончательно принимается только `solved` и вердикты, не зависящие от разбора моделью (деление на ноль, отсутствие начальной сущности, дословно стоящей в инструкции). Остальные `infeasible` считаются `unparsed`, и задачу пробует 2b. Начальная сущность, совпадающая по словам ровно с одной страницей базы («Jonas Dubois» и «Jonas T. Dubois»), тоже считается нашей ошибкой разбора, а не отсутствием.
- 2b и финальный REASON-проход: программа модели, напечатавшая последней строкой `IMPOSSIBLE` (в 2b math такой ответ REASON окончателен, программа FAST после него не запускается) (для search с `kb/` невыполнимость обычно выражается как `unparsed` «kb page or field not found»). Токены на вызов уже потрачены.

Известное ограничение: часть невыполнимых задач получает ответ (в прогонах ниже 1 из 20 и 3 из 18), если разбор приводит их к осмысленному значению, например пустое среднее даёт `0`. Это осознанное приведение: по регламенту неверно решённая задача не засчитывается; влияет ли ответ на невыполнимую задачу сверх этого, организаторы не сообщали (допущение команды).

## Траектории

Файл `trajectory.jsonl` в `HARNESS_LOG_DIR`: события всех задач в порядке выполнения, пишет `harness/scheduler.py`, каждая запись сбрасывается на диск сразу. Файл дописывается, а не перезаписывается: при повторном запуске с тем же каталогом прогоны смешиваются. В Docker по команде жюри каталог лежит в `tmpfs` и исчезает с контейнером; чтобы забрать траекторию, задайте `HARNESS_LOG_DIR` в примонтированный каталог (см. выше).

Поля записи: `phase` (1 или 2), `task_id`, `status`, `cost`, `elapsed` (с), `note`; у фазы 2 ещё `unit`, `model`, `calls`. `cost` — сумма стоимости собственных вызовов юнита (у фазы 1 — 0). `unit`: `group:<тип>:<число задач>`, `batch:<тип>:<число групп>`, `arbitrate:<task_id>`, `reason:<task_id>` или `<task_id>` для 2b. `calls` — список `{model, prompt_tokens, completion_tokens, cost}`, у неудавшихся вызовов ещё `error`. Стоимость группы записывается на её первого участника. Служебные статусы: `unit` (вызовы юнита без закрепившейся задачи), `deadline`, `budget_exhausted`, `error`, `unattributed` (расхождение с учётом бюджета, чтобы сумма `cost` по файлу равнялась расходу). Пример записи:

```json
{"phase": 2, "task_id": "data_analysis_0074", "status": "solved", "unit": "data_analysis_0074", "model": "qwen3.8-27b-noreason", "cost": 112.0, "calls": [{"model": "qwen3.8-27b-noreason", "prompt_tokens": 280, "completion_tokens": 84, "cost": 112.0}], "elapsed": 1.371, "note": "model program"}
```

Приложены траектории (`docs/trajectories/`):
- `2026-11-09-d0008e4-live4.jsonl` и `2026-11-09-d0008e4-llm3.jsonl` — два прогона ниже (коммит d0008e4);
- `2026-11-08-train.jsonl` и `2026-11-08-live-r2.jsonl` — прогоны раундов 1 и 2 на более ранних версиях кода; в первом поле `run` отличает прогоны.

## Безопасность

Изоляцию обеспечивает контейнер: корень только для чтения, без capabilities, закрытая сеть с выходом только на прокси организаторов, лимиты памяти и PID.

Единственная сетевая цель харнесса — `LLM_BASE_URL`; ключ берётся из `LLM_API_KEY`, нигде не записывается и не передаётся подпроцессам (`harness/proc.py`: `LLM_API_KEY`, `LLM_BASE_URL`, `BUDGET` убираются из окружения). Код задачи и программы модели запускаются только через `run_python`. Других адресов в коде образа нет, при запуске ничего не скачивается.

Локальных нейросетевых моделей нет. `transformers` и ещё несколько пакетов приходят транзитивно из `openjiuwen`; харнесс их не импортирует.

Код задачи и программы модели выполняются отдельным процессом на временной копии каталога задачи, с лимитами на posix: память `RLIMIT_AS` 2 ГиБ, время CPU `RLIMIT_CPU` (таймаут × 4 + 5 с), размер файла `RLIMIT_FSIZE` 1 ГиБ, вывод обрезается до 8 КБ, один поток BLAS/OpenMP. Это защита от ошибок программ, а не граница безопасности: сетевой и файловой изоляции у процесса нет, она остаётся за контейнером.

`kill`, `killpg` и чтение `/proc` используются только для завершения собственных зависших потомков по таймауту. Контейнер работает от root (без capabilities), потому что владелец смонтированного `/data/tasks` заранее неизвестен.

```bash
pip install -r requirements.txt -r requirements-dev.txt

python -m tools.bench --out <каталог> [--gen-n --seed --difficulty]   # фаза 1 без модели
python -m tools.fuzz --help; python -m tools.paraphrase --help
```
